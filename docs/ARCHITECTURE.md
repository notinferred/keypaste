## Processes today

Four processes can hold vault data. One vault has one owner, the approver in DESIGN's glossary: the desktop and `keypaste approve` take its claim (`Core/Ownership/VaultClaim.cs`) before reading the password, and serve it on a per-user, per-vault named pipe (`Core/Ipc/ApproverEndpoint.cs`) while unlocked. Either owner's `Core/Ownership/SessionAuthority.cs` records every listing, credential, run, `run --session` and token request it answers in its own home's audit log before replying, through `Core/Ownership/RequestRecorder.cs`, and refuses a release whose line it cannot write.

- The desktop app unlocks its own session (`App/Session/AppVaultSession.cs`) and locks it on idle, on `Ctrl/Cmd+L`, on quitting, on closing its window into the menu bar or tray (`App/AppTray.cs`) and, when that setting is on, on minimize; on Windows, Windows Hello can undo a lock from the key parts the last password unlock sealed (`Session/QuickUnlockCopies.cs`). It runs once per user and `KEYPASTE_HOME`: `Program.Run` takes the home's claim (`Core/Ownership/AppClaim.cs`), and a second start, or a file the system opens with the app (`Core/Ownership/HandedFile.cs`), is handed to the running copy over its same-user pipe; `--background`, which the login entry `Core/Login/` writes, opens no window. Each unlock is a `Core/Ownership/SessionLifetime.cs`, which every lock ends before the vault is disposed, withdrawing what agents have waiting. `App/Session/SessionHost.cs` serves the unlocked vault to agents under this computer's rules (`Core/Agents/`), putting a request to the person through `App/Session/WindowApprovalChannel.cs` in `Views/ApprovalWindow.axaml`, `Views/EnvApprovalWindow.axaml` or `Views/TerminalEditWindow.axaml`, and `App/Session/AppAuthority.cs` is the session and its host as launch composes them. While locked, `App/Session/LockedNotice.cs` listens on `Core/Ownership/LockedAppEndpoint.cs` and tells the person when a bridge finds the vault locked. A Run starts a project's terminal through `App/ViewModels/ProjectLaunchViewModel.cs` and `Core/Launch/`, on macOS by a launch pass (`App/Session/ProjectLaunching.cs`, flow below). `App/CrashReporting.cs` composes the run's crash reports under the terms `Views/FirstLaunchView.axaml` records (`App/Terms/`). Agents' Connect registers an AI tool through `Core/Clients/`, and Settings puts `keypaste` on a terminal's PATH through `Core/Linking/`. The [desktop guide](desktop.md) describes what the person sees.
- `keypaste approve` is started by a person in a terminal. It opens its home's audit log before its claim and the password, refusing to start without it, then holds the unlocked vault, listens on the vault's pipe and asks that person through `Cli/Approval/TerminalApprovalChannel.cs`, under this computer's rules (`agents.toml`); the channel also confirms a change that gives an agent more, asked for by `keypaste clients` or the prompt's `[a]`, and a terminal's edit to the vault's items, before `keypaste approve` saves it in the vault under its claim. Ctrl+C, SIGTERM and SIGHUP end its lifetime the same way.
- `keypaste mcp` is started by the MCP client, never opens a vault, forwards each request to the vault's owner over the pipe and writes an audit line only for a call no owner recorded. Under `--allow-run` it also starts a command an agent names, after the owner's approval, with the approved set in its environment (`Mcp/Tools/RunTool.cs`). Before it refuses a request for want of an owner, `Mcp/LockedApp.cs` connects to an app locked on the vault, and when one answers the refusal says so. `Program.StartsBridge` in `Keypaste.Cli` decides from the arguments alone, before any vault access: `mcp serve`, `mcp setup` and `mcp policy` go to `CliApp.Run`, which refuses them as removed spellings, and every other `keypaste mcp`, its help included, to `BridgeEntry.RunAsync`.
- The browser relay is `keypaste` as a browser starts it for keypaste's extension, through the manifest Settings › Browser fill or `keypaste browser` wrote (`Core/Browser/BrowserHosts.cs`), with the caller's origin or add-on ID as its arguments, which `Program.cs` hands to `BrowserEntry.RunAsync` before any vault access. It never opens a vault: it finds the vault's owner as `keypaste mcp` with no arguments does, ends the extension's NaCl box session, answers each action keypaste refuses itself with KeePassXC's error code, and sends the owner only typed pairing, pairing-check, fill and lock requests, as a browser's attachment naming the build the browser named, which the owner admits for those four alone. It holds its link to the owner with a read pending, so the owner's lock is told to the extension as `database-locked`; with nothing holding the vault unlocked it answers error 1, knocking on the locked app's pipe when the extension asks to unlock. It writes no audit line. The owner tells a browser's attachment its database hash, pairs a browser only while the person armed pairing, with Settings › Browser fill's Pair a browser or `keypaste approve --pair-browser`, and only once they confirm it in the app's `Views/PairingWindow.axaml` or at `keypaste approve`'s terminal, keeping each pairing in the vault's `.keypaste/browsers` through `Core/Ownership/SessionBrowsers.cs`, and until 8.3a2 refuses every fill.
- `keypaste run` opens the vault, reads an env set, closes the vault and starts the child with the values in its environment through the same `Core/Launch/EnvLaunch.cs` as the app. It takes no claim. With `--session` it opens nothing: it attaches to the owner's endpoint as the bridge does and sends an env request, which `SessionAuthority` resolves through `SessionEnvResolver` under the attached session, asking through the owner's own `ApprovalGate` and channel, and starts the child with the whole set the reply carries. The run Terminal starts for the app on macOS asks the app's launch endpoint rather than the vault's and carries the app's launch pass in `KEYPASTE_LAUNCH`, which the owner takes in place of asking and no child inherits. With `--token` it sends a token env request the owner verifies against `Core/Tokens/` instead of asking, and with `--bundle` it opens a token bundle with no vault or pipe.
- `keypaste lock` attaches to the owner as the bridge does and locks it. `keypaste doctor` attaches the same way, naming no AI tool, only to learn whether the owner answers and its version, which every attach reply carries; it never connects to a locked app's pipe, opens no vault, writes nothing, and starts only the `keypaste` each AI tool registers, with `--version` and `mcp --help`, and the one PATH finds, with `--version` (`Core/Health/`). `keypaste` alone on a terminal reads the vault's header, the AI tools' files and the owner's answer the same way and starts nothing (`Commands/StatusCommand.cs`). `keypaste share` opens the vault under its claim, seals one field and uploads the ciphertext to keypaste.com's `/api/share`, which `site/src/share.js` serves.

A credential request runs: MCP client → `Mcp/Tools/RequestCredentialTool.cs` → `Mcp/ApproverConnection.cs`, which attaches to the owner's session naming its vault → `Core/Ipc/ApproverClient.cs` → pipe → `Core/Ipc/ApproverListener.cs` in the owner → `Core/Ownership/SessionAuthority.cs`, which refuses a request not from its current session → `Core/Approval/ApproverHandler.cs`, which resolves the entry, re-checks exposure, refuses a Blocked category, honours a recent refusal, releases under an Allow or asks the person, and only then reads one field → the authority commits the release only while the session's lifetime is live → the authority records the line in its home's log, refusing a release it cannot record → reply naming the session and saying it was recorded.

A save request runs the same way to `SessionAuthority`, then `Core/Ownership/SessionSaver.cs`, which checks the place with `Core/Editing/ValueSaves.cs` and what the agent can see, asks the person for the value through the gate, and writes it with the terminal's edits under the owner's claim; the reply says only whether it was saved.

A browser's request runs: keypaste's extension → the browser, which starts `keypaste` with its caller's identity → `Program.cs` → `Browser/Relay.cs`, which opens the extension's box and checks its nonce → `Core/Ipc/BrowserLink.cs`, attached as a browser → pipe → `Core/Ipc/ApproverListener.cs` → `Core/Ownership/SessionAuthority.cs`, which admits it only on a browser's attachment to its current session and has the `Core/Browser/IBrowserRequests.cs` it was given, `Core/Ownership/SessionBrowsers.cs` in both owners, decide a pairing, check or fill, binding the connection to the pairing a pairing or a check proved and refusing a fill under any other, or locks for a lock → reply → the relay seals the answer under the request's nonce incremented.

On macOS a Run confirmed in the app runs: `App/ViewModels/ProjectLaunchViewModel.cs` → the app's `SessionAuthority.IssueLaunch`, which keeps the pass in `Core/Approval/LaunchPasses.cs` → a request file → `/usr/bin/open -b com.apple.Terminal` on the launcher → Terminal → the launcher, which claims and deletes the request → the bundle's `keypaste run --session` → pipe → the app's launch endpoint, `Core/Ownership/LaunchEndpoint.cs` → `SessionAuthority`, which takes the pass and releases the set the card named without asking → the authority records the line in its home's log → reply.

## Tests, gates and delivery

- `tests/Keypaste.<Project>.Tests` mirror the projects; `Keypaste.App.Windows.Tests` runs against the app's Windows target. The helper projects `TxfContender`, `PoolStarver`, `VaultSaver`, `MinimizeObserver`, `AppDriver`, `FakeMcpClient`, `FakeBrowser` and `EnvReporter` are unshipped processes that particular probes and gates drive; `AppDriver` performs one desktop act through the screen's view model, or holds a vault unlocked and served as the app does, with the app's prompt window drawn on a headless display and clicked, or runs the app's own start there, or stands in for keypaste.com's crash route on loopback, or reports the sequence the unlocked session would type into a window of a given title, typing nothing. `FakeMcpClient` builds as `claude` and answers Claude Code's `mcp add`, `remove` and `list`, so the connect gate never writes a real client's configuration. `EnvReporter` is the child the app's Run starts in its tests, reporting its own environment over a pipe. `FakeBrowser` stands in for keypaste's extension: its `ExtensionClient` speaks the extension's protocol to a host's standard input and output, which the relay's tests drive in their own process, and its program starts a host with each browser's arguments, or finds the manifest where a browser looks under given folders and starts it as that browser does, and prints each answer, which `Keypaste.Processes.Tests.BrowserHostTests` reads.
- `scripts/verify.sh`, or `verify.ps1` in PowerShell, is the local verification entry point ([CONTRIBUTING](../CONTRIBUTING.md#verification)). `Keypaste.Core.Tests.KeePassXC` holds the permanent KeePassXC compatibility checks, every workflow on vaults KeePassXC made read back by real `keepassxc-cli`, and the `scripts/verify-keepassxc-*.sh` left check the shipped binaries; `Keypaste.Processes.Tests` drives the built `keypaste`, `keypaste mcp`, `keypaste-app` and the desktop driver as separate processes, for what only crosses a process boundary, and `verify-mcp-stdio.sh`, `verify-approval-e2e.sh`, `verify-policy-e2e.sh`, `verify-log-chain.sh`, `verify-run-injection.sh` and `verify-run-signals.sh` drive the shipped processes; `verify-real-tools.sh`, run only by ci's `tools` jobs, connects the built `keypaste` to the real AI tools; `verify-demo.sh` checks published transcripts against the binaries. The gates share `scripts/lib/common.sh`, and the KeePassXC gates also `scripts/lib/kpxc.sh`.
- Packaging and release: `release-targets.json` defines targets; `build-*.sh`, `publish-desktop-bridge.sh`, `sign-windows.sh`, `publish-release.sh`, `release-completion.sh` and `require-*.sh` implement [RELEASE](RELEASE.md). `packaging/claude-desktop/` is the Claude Desktop extension, whose Node launcher starts the installed `keypaste mcp` with setup's arguments and carries no copy of keypaste; ci's checks job packs and checks it with `build-claude-desktop-extension.sh`, and nothing publishes it yet (G.6b).
- `.github/workflows/`: `ci.yml` (backend), `app.yml` (desktop), `release.yml`, `install*.yml`, `upgrade-desktop.yml`, `dco.yml` and `dev.yml`, which runs one verify.sh profile on one hosted runner, or installs an app run's packages and performs R.1a's acts.
- `site/` is keypaste.com; [site/README.md](../site/README.md) owns its deployment. Its content pages and topic map live in InfernoCMS at `https://infernocms.com`, site `keypaste`: `site/web/scripts/pull.mjs`, a pinned copy of InfernoCMS's `/pull.mjs`, writes them into `site/web/src/content/docs/` and their JSON-LD into `site/web/src/generated/` before each build, and neither directory is tracked. A publish there rebuilds the site through a Workers Builds deploy hook.
