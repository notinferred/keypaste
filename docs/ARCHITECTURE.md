Where the code is, so a task starts from the right files instead of a search of the whole tree. [PRODUCT](PRODUCT.md) owns intent and laws; this map changes only when a project, entry point or process boundary changes.

## Processes today

Four processes can hold vault data. One vault has one owner: the desktop and `keypaste approve` take its claim (`Core/Ownership/VaultClaim.cs`) before reading the password, and serve it on a per-user, per-vault named pipe (`Core/Ipc/ApproverEndpoint.cs`) while unlocked (D-0309). Either owner's `Core/Ownership/SessionAuthority.cs` records every listing, credential, run, `run --session` and token request it answers in its own home's audit log before replying, through `Core/Ownership/RequestRecorder.cs`, and refuses a release whose line it cannot write (D-0439).

- The desktop app unlocks its own session (`App/Session/AppVaultSession.cs`) and locks it on idle, on `Ctrl/Cmd+L`, on quitting, on closing its window into the menu bar or tray (`App/AppTray.cs`), where the process stays locked, and, when that setting is on, on minimize. On Windows such a lock, or idleness, can be undone with Windows Hello, which opens the file again from the key parts the last password unlock sealed, after taking the vault's claim, while every other lock needs the password (D-0550, D-0551). Started with `--background` by the per-user login entry `Core/Login/` writes, it opens no window while it stays in the tray (D-0385, D-0386). It runs once per user and `KEYPASTE_HOME`: `Program.Run` takes the home's claim (`Core/Ownership/AppClaim.cs`), and a second start asks the holder over its same-user pipe to show its window and exits (D-0397). Under that claim `Program.StartCrashReports` composes the run's crash reports (`App/CrashReporting.cs`), which set the process's exception hooks and the run marker; the first start shows the terms of use (`App/Terms/`) and the crash-report choice before the unlock screen, and an exception on the UI thread locks, clears the clipboard and quits (D-0594 to D-0598). While locked under that claim, `App/Session/LockedNotice.cs` listens on `Core/Ownership/LockedAppEndpoint.cs` for the vault the unlock screen shows and the chosen vault, and the first bridge to connect after a lock has it show `Views/LockedNoticeWindow.axaml`, whose Open keypaste puts that vault on the unlock screen (D-0466). Each unlock is a `Core/Ownership/SessionLifetime.cs`, and every lock ends it before the vault is disposed, withdrawing what agents have waiting and zeroing their grants (D-0313). `App/Session/SessionHost.cs` serves the unlocked vault to agents under the settings the vault holds for each (`Core/Agents/`): listings are answered, and each credential request is put to the person in the prompt window `App/Session/WindowApprovalChannel.cs` shows (`Views/ApprovalWindow.axaml`) unless the agent is Automatic for it, each `keypaste run --session` request in `Views/EnvApprovalWindow.axaml`, and each terminal's edit in `Views/TerminalEditWindow.axaml`, saving it through the same unlock's session, and Agents' Show the prompt brings the waiting window forward through it, disarmed for another second (D-0456); it opens the home's audit log at the first request, or at a Run's check before its card, and, after an open that failed, again at the next. `App/Session/AppAuthority.cs` is the two together as launch composes them: disposing it is quitting, and its status is read from the authority answering agents (D-0321). Env Sets launches a project's terminal through `App/ViewModels/ProjectLaunchViewModel.cs`: the session resolves the set under the confirmation it shows, and `Core/Launch/` starts the terminal detached (D-0340). On macOS it hands Terminal no value: after the same confirmation it has the app's authority issue a launch pass, writes the run's request with `Core/Launch/TerminalRequests.cs` and, through `App/Session/ProjectLaunching.cs`, opens Terminal on the bundle's launcher, `packaging/macos/keypaste-launch.command`, whose `keypaste run --session` presents the pass to the app's launch endpoint (D-0451, D-0452). `SessionHost` builds each unlock's authority with `SessionServer.Build` before binding anything, then on macOS binds that endpoint, `Core/Ownership/LaunchEndpoint.cs`, under a random name it picks once and answering only an attachment and an env request held to its pass, beside the vault's, so a Run starts whatever agents meet. Agents lists the AI tools `Core/Clients/McpToolSurvey.cs` finds on this computer, looked for in the background each time it opens, and a tool's Connect runs that tool's own registration command or edits its configuration file, and starts the registered `keypaste mcp` once to check it, both through `Core/Clients/` (D-0455); the desktop packages carry the combined `keypaste` binary, which a client connected from an AppImage starts through the Linux link below, made first when it is absent (D-0334, D-0418, D-0435). A terminal finds that `keypaste` through the MSI's per-user PATH entry on Windows and, elsewhere, through the link Settings makes with `Core/Linking/`: on Linux a script in `~/.local/bin` that starts the AppImage with `cli`, which each start of a newer copy re-points in `Program.Run` before any vault is open, a start handed to a running copy included, and on macOS a link in `/usr/local/bin` that `osascript` makes as root behind the administrator dialog; a file keypaste did not write there is replaced only once the person confirms, and kept beside it (D-0431, D-0432).
- `keypaste approve` is started by a person in a terminal. It opens its home's audit log before its claim and the password, refusing to start without it, then holds the unlocked vault, listens on the vault's pipe and asks that person through `Cli/Approval/TerminalApprovalChannel.cs`, under each agent's settings as the vault holds them; the channel also confirms a change that gives an agent more, asked for by `keypaste clients`, the prompt's `[a]` or the agent's own tool, and a terminal's edit to the vault's items, before `keypaste approve` saves it in the vault under its claim (D-0445, D-0464). Ctrl+C, SIGTERM and SIGHUP end its lifetime the same way.
- `keypaste mcp` is started by the MCP client, never opens a vault, forwards each request to the vault's owner over the pipe and writes an audit line only for a call no owner recorded. Under `--allow-run` it also starts a command an agent names, after the owner's approval, with the approved set in its environment (`Mcp/Tools/RunTool.cs`, D-0358). Before it refuses a request for want of an owner, `Mcp/LockedApp.cs` connects to an app locked on the vault, and when one answers the refusal says so (D-0466). `Program.StartsBridge` in `Keypaste.Cli` decides from the arguments alone, before any vault access: `mcp serve`, `mcp setup` and `mcp policy` go to `CliApp.Run`, which refuses them as removed spellings (D-0470), and every other `keypaste mcp`, its help included, to `BridgeEntry.RunAsync` (D-0418).
- The browser relay is `keypaste` as a browser starts it for KeePassXC-Browser, with the caller's origin or add-on ID as its arguments, which `Program.cs` hands to `BrowserEntry.RunAsync` before any vault access (D-0624). It never opens a vault: it finds the vault's owner as `keypaste mcp` with no arguments does, ends the extension's NaCl box session, answers each action keypaste refuses itself with KeePassXC's error code, and sends the owner only typed pairing, pairing-check, fill and lock requests, as a browser's attachment naming the build the browser named, which the owner admits for those four alone (D-0625 to D-0627). It holds its link to the owner with a read pending, so the owner's lock is told to the extension as `database-locked`; with nothing holding the vault unlocked it answers error 1, knocking on the locked app's pipe when the extension asks to unlock (D-0466, D-0628). It writes no audit line. The owner tells a browser's attachment its database hash, pairs a browser only while the person armed pairing, with Settings › Browser fill's Pair a browser or `keypaste approve --pair-browser`, and only once they confirm it in the app's `Views/PairingWindow.axaml` or at `keypaste approve`'s terminal, keeping each pairing in the vault's `.keypaste/browsers` through `Core/Ownership/SessionBrowsers.cs`, and until 8.3a2 refuses every fill (D-0633 to D-0637).
- `keypaste run` opens the vault, reads an env set, closes the vault and starts the child with the values in its environment through the same `Core/Launch/EnvLaunch.cs` as the app. It takes no claim. With `--session` it opens nothing: it attaches to the owner's endpoint as the bridge does and sends an env request, which `SessionAuthority` resolves through `SessionEnvResolver` under the attached session, asking through the owner's own `ApprovalGate` and channel, and starts the child with the whole set the reply carries (D-0341). The run Terminal starts for the app on macOS asks the app's launch endpoint rather than the vault's and carries the app's launch pass in `KEYPASTE_LAUNCH`, which the owner takes in place of asking and no child inherits (D-0451, D-0452). With `--token` it sends a token env request the owner verifies against `Core/Tokens/` instead of asking, and with `--bundle` it opens a token bundle with no vault or pipe (D-0352, D-0353).
- `keypaste grants` and `keypaste lock` attach to the owner as the bridge does and list or end its grants, or lock it (D-0351). `keypaste doctor` attaches the same way, naming no AI tool, only to learn whether the owner answers and its version, which every attach reply carries; it never connects to a locked app's pipe, opens no vault, writes nothing, and starts only the `keypaste` each AI tool registers, with `--version` and `mcp --help`, and the one PATH finds, with `--version` (`Core/Health/`, D-0467). `keypaste` alone on a terminal reads the vault's header, the AI tools' files and the owner's answer the same way and starts nothing (`Commands/StatusCommand.cs`, D-0471). `keypaste share` opens the vault under its claim, seals one field and uploads the ciphertext to keypaste.com's `/api/share`, which `site/src/share.js` serves (D-0354).

A credential request runs: MCP client → `Mcp/Tools/RequestCredentialTool.cs` → `Mcp/ApproverConnection.cs`, which attaches to the owner's session naming its vault → `Core/Ipc/ApproverClient.cs` → pipe → `Core/Ipc/ApproverListener.cs` in the owner → `Core/Ownership/SessionAuthority.cs`, which refuses a request not from its current session (D-0310) → `Core/Approval/ApproverHandler.cs`, which resolves the entry, re-checks exposure, consults the grant cache, a recent refusal and the agent's mode, asks the person and only then reads one field → the authority commits the release only while the session's lifetime is live (D-0313) → the authority records the line in its home's log, refusing a release it cannot record (D-0439) → reply naming the session and saying it was recorded.

A browser's request runs: KeePassXC-Browser → the browser, which starts `keypaste` with its caller's identity → `Program.cs` → `Browser/Relay.cs`, which opens the extension's box and checks its nonce → `Core/Ipc/BrowserLink.cs`, attached as a browser → pipe → `Core/Ipc/ApproverListener.cs` → `Core/Ownership/SessionAuthority.cs`, which admits it only on a browser's attachment to its current session and has the `Core/Browser/IBrowserRequests.cs` it was given, `Core/Ownership/SessionBrowsers.cs` in both owners, decide a pairing, check or fill, binding the connection to the pairing a pairing or a check proved and refusing a fill under any other, or locks for a lock → reply → the relay seals the answer under the request's nonce incremented.

On macOS a Run confirmed in the app runs: `App/ViewModels/ProjectLaunchViewModel.cs` → the app's `SessionAuthority.IssueLaunch`, which keeps the pass in `Core/Approval/LaunchPasses.cs` → a request file → `/usr/bin/open -b com.apple.Terminal` on the launcher → Terminal → the launcher, which claims and deletes the request → the bundle's `keypaste run --session` → pipe → the app's launch endpoint, `Core/Ownership/LaunchEndpoint.cs` → `SessionAuthority`, which takes the pass and releases the set the card named without asking → the authority records the line in its home's log (D-0439) → reply.

## Tests, gates and delivery

- `tests/Keypaste.<Project>.Tests` mirror the projects; `Keypaste.App.Windows.Tests` runs against the app's Windows target. The helper projects `TxfContender`, `PoolStarver`, `VaultSaver`, `VaultRestorer`, `MinimizeObserver`, `AppDriver`, `FakeMcpClient`, `FakeBrowser` and `EnvReporter` are unshipped processes that particular probes and gates drive; `AppDriver` performs one desktop act through the screen's view model, or holds a vault unlocked and served as the app does, with the app's prompt window drawn on a headless display and clicked, or runs the app's own start there, or stands in for keypaste.com's crash route on loopback, or reports the sequence the unlocked session would type into a window of a given title, typing nothing. `FakeMcpClient` builds as `claude` and answers Claude Code's `mcp add`, `remove` and `list`, so the connect gate never writes a real client's configuration. `EnvReporter` is the child the app's Run starts in its tests, reporting its own environment over a pipe. `FakeBrowser` stands in for KeePassXC-Browser: its `ExtensionClient` speaks the extension's protocol to a host's standard input and output, which the relay's tests drive in their own process, and its program starts a host with each browser's arguments and prints each answer, which `scripts/verify-browser-host.sh` and `verify-keepassxc-workflows.sh` read.
- `scripts/verify.sh`, or `verify.ps1` in PowerShell, is the local verification entry point ([CLAUDE.md](../CLAUDE.md)). `scripts/verify-keepassxc-*.sh` are the permanent KeePassXC compatibility gates, one per vault feature, and `verify-keepassxc-workflows.sh` runs every workflow through the CLI and the desktop on vaults KeePassXC made; `verify-mcp-stdio.sh`, `verify-approval-e2e.sh`, `verify-policy-e2e.sh`, `verify-log-chain.sh`, `verify-session-authority.sh`, `verify-desktop-approval.sh`, `verify-connect-client.sh`, `verify-crash-report.sh`, `verify-browser-host.sh` and `verify-run-*.sh` drive the shipped processes; `verify-real-tools.sh`, run only by ci's `tools` jobs, connects the built `keypaste` to the real AI tools; `verify-demo.sh` checks published transcripts against the binaries. The gates share `scripts/lib/common.sh`, and the KeePassXC gates also `scripts/lib/kpxc.sh`.
- Packaging and release: `release-targets.json` defines targets; `build-*.sh`, `publish-desktop-bridge.sh`, `sign-windows.sh`, `publish-release.sh`, `release-completion.sh` and `require-*.sh` implement [RELEASE](RELEASE.md). `packaging/claude-desktop/` is the Claude Desktop extension, whose Node launcher starts the installed `keypaste mcp` with setup's arguments and carries no copy of keypaste; ci's checks job packs and checks it with `build-claude-desktop-extension.sh`, and nothing publishes it yet (G.6b).
- `.github/workflows/`: `ci.yml` (backend), `app.yml` (desktop), `release.yml`, `install*.yml`, `upgrade-desktop.yml`, `dco.yml` and `dev.yml`, which runs one verify.sh profile on one hosted runner, or installs an app run's packages and performs R.1a's acts.
- `site/` is keypaste.com; [site/README.md](../site/README.md) owns its deployment.
