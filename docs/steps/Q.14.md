# Q.14 — Use the system's notifications

Implemented 2026-11-05 on `q14-notifications`, source only; no platform's package has shown a notification to a person. Last fast tier: ci 42127519563, green, at `f57f5e0f`; only this record's later edits follow it.

## Amendments

The founder's selection added what follows, each applied: a notification carries nothing of the request, it never answers one, a stale press reaches nothing, a burst does not flood, and the window stays as the fallback. Windows does not meet the row's second half: its locked notice stays the window, as Decisions says, and whether to add what would change that is the founder's.

## What it does

A request whose prompt appears while no keypaste window has focus also posts `SystemNotice.RequestWaiting`, at most one every 30 seconds. The locked notice posts `SystemNotice.VaultLocked` first and falls back to the window, and on Windows is always the window. Posting runs off the UI thread once the prompt is up; only the background check comes before the prompt shows. Avalonia 12.1 offers no system notification, only `WindowNotificationManager` inside a window, so each platform is reached behind `ISystemNotifications`: macOS's UserNotifications through the Objective-C runtime as `MacDock` does, Windows's toast through the Windows target's WinRT projection, and `org.freedesktop.Notifications` through `Tmds.DBus.Protocol`.

The dependency: `Tmds.DBus.Protocol` 0.94.1 was already in every lock file under `Avalonia.FreeDesktop`, and is now named at the same version, so nothing new ships. It is established, maintained open source used by Avalonia, outside the secret path (PRODUCT §4.9), and speaks to the local session bus only. `DesktopNotifications`, the one library that wraps these platforms, has no macOS implementation and one maintainer.

## Decisions

- **The agent's name stays off a notification.** A label is written by the agent's side and can be anything, a customer or a key's name included, so it is not safe on a lock screen; the prompt shows it one press away. Every word is a constant, so no item, field, group, value, vault, agent or reason has anywhere to go.
- **The vault's file name stays off too.** A file name can say whose it is. The notification reads "An agent asked for a locked vault" and its press still puts the right vault on the unlock screen from memory. The window keeps naming it, since it never reaches the lock screen.
- **Which is used.** A request's prompt always appears, so a failed post loses nothing. The locked notice is always the window on Windows. On macOS it is the window when the process is not in an app bundle, permission is refused or was never granted, alerts are off in the system's settings, the add is answered with an error, or any of these has not answered in 5 seconds, which includes a permission dialog not yet answered. On Linux it is the window when there is no session bus, no notification server or a server that shows no actions, or the server has not answered in 5 seconds. It is the window when posting throws. Elsewhere it is the notification. Focus and a desktop's do-not-disturb are not seen, so the system may hold a notice and no window appears.
- **Windows keeps the window for the locked notice.** A toast there has no `ToastActivatorCLSID` on the MSI's shortcut and no COM activator, which Microsoft's ToastAndCallback walkthrough (`author-coclasses.md` in windows-dev-docs, the only page of this I could read in full) names as the mechanism by which a press from a toast or Action Center reaches an app; how `toast.Activated` and Notification Center behave without one has not been observed. An accepted toast that leaves with its banner would lose a notice nothing else tells, so it is not posted; a request's toast loses nothing, as its prompt is up. For the same reason `Failed` is not read: only a request's toast posts, and nothing waits on its answer. Toasts of either notice stop below Windows 10 2004 (build 19041), which the supported floor of 1809 includes: there a request posts nothing.
- **macOS asks the add and the settings.** The add's error is the post's answer, and alert style None or a disabled alert setting counts as unable to post, so a refused add reaches the window. `--selftest` in a bundle without permission makes an add, which the system refuses without showing anything, so the packaging job holds that block too; a granted add has still never run.
- **Linux sends a named button as well as `default`.** The specification lets a server keep `default`'s label off the screen; a server showing both shows the same words twice. A request's expiry is the 45-second answer window rather than never, so a run that dies leaves its words no longer on a server honouring it; T-51 records the rest.
- **Spacing is 30 seconds and a request inside it posts nothing.** The prompt still appears. Being time-sensitive a notice can pass Focus, and an agent chooses when it asks.
- **Requests of every kind post the same words**, since all reach the channel through one path: credential, run, env, access change, terminal edit and pairing.
- **A press has no request in it.** It calls `BringForward`, which acts on whatever prompt is up, and `RaisedNotice` drops it once its notice was removed, so a late press changes nothing, even with another prompt on screen.
- **`--selftest` reads the notification permission in a macOS bundle**, having set up the delegate and categories, and `build-macos-app.sh` requires the line, because a mistake in that path ends the process rather than failing. It asks the person nothing.
- **Windows's scenario is `urgent`**, the closest to time-sensitive, with high priority. Linux's is critical urgency, which many servers keep until `CloseNotification` whatever its expiry. macOS's is the time-sensitive interruption level, which without the entitlement shows as an ordinary one.

## Limits and follow-ups

Implemented only, in RELEASE's terms. Not run on any machine: `requestAuthorization`'s answer, a granted add and a press on macOS, whether an unsigned bundle is refused or gets a dialog, the toast's press on Windows, its stay in Notification Center and whether a press raises the prompt, a real Linux server, and Wayland's activation. No process gate reaches the real notification path: `AppLaunch` gives the driver `NoSystemNotifications`, and `dev.sh --acts` over installed packages was not run for this step, so only the bundle's `--selftest` calls the platform. BACKLOG holds these for R.1a's walk. 3.5b's signature must carry `com.apple.developer.usernotifications.time-sensitive`, or a request's notification will not pass Focus; RELEASE says so. `THIRD_PARTY_NOTICES.md` is not changed: it does not list Avalonia or this client today, and what it should list is the founder's.
