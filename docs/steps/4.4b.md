# 4.4b — Own session startup and shutdown from the app

Completed 2026-09-23 on `main` above `b490214`, source only. [PRODUCT](../PRODUCT.md) and [STEPS](../STEPS.md) own scope and the plan; this record is what the step did and is not revised afterwards.

## Scope as selected

**Verify (V-4.4b):** with no terminal process running, launching the app and unlocking lets a real `keypaste-mcp` request reach the app's session. Locking and quitting each make the next request fail as locked or absent, with no owner left behind. Killing the app mid-session and relaunching leaves no stale endpoint answering, and requests are refused until a new unlock. With `keypaste agent` holding the vault first, the app's unlock is refused naming it, and the status shows the agent as the owner. A status read from a listening pipe, or a lock observed only in a view model, does not pass.

The founder approved the plan as written. Two parts of it came out differently in the building, and are recorded here:

- The plan listed "the driver builds its own host rather than `AppAuthority`" as a mutation. That is a change to the test harness, not to the product, so it was not run. What stands in for it is that the driver now has no host of its own to build: its `hold` composes `AppAuthority` exactly as launch does.
- The plan's first status mutation, "the status ignores the authority's lifetime", was run as planned and survived, because the host's own read also goes through the authority. The mutation that matches the Verify's warning, a status read from the endpoint alone, changes both reads together; it was run and caught (below).

## Evidence

**Tests**, over real pipes:

- `AppAuthorityTests`, 5, new:
  - The status goes from locked at launch to serving on unlock, naming the session a real attachment is answered under and this process as a `DesktopApp` owner. Lock and quit each make it locked, leave no endpoint answering and leave the claim free; the second unlock is a new session.
  - After a sleep past the idle deadline, with the listener still up, the status is not serving.
  - An endpoint the `KEYPASTE_APPROVER` setting cannot name is reported as not serving while the vault is unlocked.
  - With a `TerminalAgent` claim held, the unlock screen's refusal and owner line name the agent, the status is `HeldBy` the agent and Agent Activity says the same sentence. Typing clears the refusal and keeps the owner line. Once the claim is released the unlock succeeds, the line goes and the status is serving.
  - Quitting answers a request waiting at a held prompt as `vault-locked`, naming its session.
- `LockBoundaryTests`: the shutdown case of its theory moved to `AppAuthorityTests`, so quitting is tested through the composition launch runs. Its other seven cases are unchanged and pass.
- `VaultClaimTests`, 1 new and 1 extended: a refused claim returns the holder as a `VaultOwner`, and a claim taken returns none.

**Gate**, [verify-session-lifecycle.sh](../../scripts/verify-session-lifecycle.sh): the shipped Release `keypaste` and `keypaste-mcp` against `Keypaste.AppDriver hold`, which now prints a `status` line read from `AppAuthority.Status` after each transition and takes `--locked` to start at the unlock screen as a launch does.

1. With no terminal process, the app launched locked reports `status locked`, and a listing and a request are denied, audited with no session. After `unlock`, a real listing is answered and audited naming the session the status reports.
2. After `lock`, both calls are denied reaching no session, and another app opens the vault.
3. After a new unlock, a request waiting at the app's prompt is answered by quitting as `vault-locked`, naming that session. The status reads locked, later calls are denied, and another app opens the vault.
4. An app killed with a request waiting leaves that request denied. On Linux the gate first checks that the killed process's socket file is still there, so the takeover is not vacuous. Later calls are denied. A relaunch with `--locked` reports locked and denies. After `unlock` it serves a new session on the same endpoint, and a listing names it.
5. With `keypaste agent` holding the vault, the app's unlock exits 1 with a refusal naming the agent's process, an owner line and `status held by keypaste agent (process P)`, and it never serves. A listing is still answered by the agent, naming the agent's session.

The gate passed on Windows 10 in 49 s. With self-contained non-AOT linux-x64 builds of this tree, it passed in the `scripts/container` Ubuntu 24.04 image in 50 s, stale-socket check included. In the same image, [verify-session-authority.sh](../../scripts/verify-session-authority.sh), [verify-lock-boundary.sh](../../scripts/verify-lock-boundary.sh), SIGTERM step included, and [verify-current-state.sh](../../scripts/verify-current-state.sh) passed on the changed driver, as they did on Windows. The gate runs in the `desktop` profile, which `app.yml` runs on `ubuntu-24.04`, and `app.yml` now triggers on it.

## Limits and follow-ups

The status check that the accept loop is still running is not exercised by any test, as the mutation table says. It is kept because a listener that has stopped accepting must not read as serving.

The app's quit path in `App.axaml.cs` now disposes `AppAuthority`, and the gates drive that object. No gate launches the real Avalonia process: the driver runs the same composition without a window. A person's quit through the window manager, and sleep and restore, remain F.2b3's to observe.

The owner line reports the holder as it was when the unlock was refused. If the agent stops later, the line stays until the person selects a vault or tries again.

On Windows a killed app's pipe disappears with the process, so the stale-endpoint step checks only that nothing answers. The takeover of a leftover socket file is Linux's, observed in the container and in `app.yml`. macOS is not run.

The bridge's refusal wording when nothing holds the vault still points at `keypaste agent`, because the app cannot approve until 4.4.
