# 2.6a — Connect an MCP client from the app

Completed 2026-09-24 on `main` above `3f64ba5`, source only; the CI evidence is from branch `step/2.6a` at `530b6b8`, whose code and workflows are those merged. [PRODUCT](../PRODUCT.md) and [STEPS](../STEPS.md) own scope and the plan; this record is what the step did and is not revised afterwards.

## Scope as selected

**Build:** the app offers the clients `keypaste setup` supports (`Core/Clients/McpClientCatalog.cs`) for the vault it has unlocked, with the exposure the person selects. Before anything is written it shows the exact command it will run or the block it will print, including `--vault` and `--expose`, and it acts only on an explicit confirmation. Where a client has its own registration command, the app runs that, as `setup` does; otherwise it shows the block to paste and claims nothing. A connection check starts `keypaste-mcp` with the configured arguments and sends one `list_entry_names` and one `request_credential` through the app's session, so a real prompt, answer and audit line result. Removing the connection runs the client's own removal, so that client can no longer start the bridge for this vault. No master password, keyfile or session identifier reaches client configuration. Traces to PRODUCT §§1, 2 and 3.2.

**Verify (V-2.6a):** from the unlocked app, connecting a client whose registration command is available registers exactly what the preview showed, and cancelling writes nothing. The check raises the app's prompt, and after Approve the audit file holds a prompted grant naming the app's session and the chosen label. After removal the client no longer lists the server, and its configuration holds no vault secret before or after. A preview composed by the view model rather than the core catalogue, or a check that only opens the pipe, does not pass.

The founder approved the plan with two amendments made while planning:

- **The desktop packages carry the bridge.** Exploration found that the MSI and AppImage shipped only `keypaste-app`, so an installed app had nothing to register. The founder chose to package `keypaste-mcp` in this step rather than leave it to T5. An AppImage mounts at a new temporary path on every launch, so the founder chose to register the image file itself with `mcp`, which `AppRun` dispatches to the bridge (D-0334).
- **Which entry the check asks for.** With one listed name the check asks for it at once. With several, the person picks from the listing, with the first selected (D-0335).

## What changed for users

- **Connect a client.** Agent Activity has a section, under the status line, for the vault the app has unlocked. It offers Claude Code, Codex, Cursor and Claude Desktop, a label (the client's id by default) and an exposure field that leaves the bridge's default `env/**` when empty. Preview connect shows exactly what will run. For Claude Code and Codex that is two commands: the client's removal of any earlier keypaste entry, then its `mcp add` with the `keypaste-mcp` path, `--vault`, `--client-label` and each `--expose`. Run it executes that same plan, and nothing else, then says whether it connected or what the client refused in its own words. Cancel, and any change to the client, label or exposure, drops the preview, so an old plan cannot run. A client whose command cannot be started is said to be not installed, and nothing is offered. A label the audit log would rewrite, or an exposure the bridge would refuse, is refused before anything is shown. For Cursor and Claude Desktop the section shows the block to paste and says keypaste wrote nothing.
- **Where the bridge comes from.** The app registers the `keypaste-mcp` beside it, or else the first one on PATH, and says where it looked when there is none. Run from inside its AppImage, it registers the `.AppImage` file with `mcp` instead of a path inside the mount.
- **Check the connection.** This starts the registered command line as the client would, with the app's own environment, so the bridge reaches the app's session and writes the audit log the history reads. It introduces itself as `keypaste-check`, lists the names the exposure allows, and asks for the password of the only one or of the one picked, with the reason "Connection check from the keypaste app. The value is discarded unread." The request opens the app's prompt window like any other. Approve reports that the password was released and discarded unread; Deny reports the refusal in the bridge's words. Either way the audit record appears in this session's history below. Locking, or leaving the screen, while the check waits ends its bridge, and the request is withdrawn.
- **Remove.** Preview remove shows the client's own removal, and Run it runs it, leaving the client's other servers alone. For a client configured by file it says what to delete by hand and claims nothing.
- **The packages.** Every desktop payload `app.yml` builds, and the upgrade candidates, now carry the NativeAOT `keypaste-mcp` beside `keypaste-app`, built from the same project as the CLI/MCP archives. The MSI check requires the extracted `keypaste-mcp.exe` to answer `--help`, and the AppImage check requires `AppRun mcp --help` to reach the bridge.
- **`keypaste setup`** now composes and runs the same core plans as the app. Its output is unchanged, except that `--dry-run` quotes an argument that contains a space, and a Cursor or Claude Desktop block now carries `--label` when one is given.

## Limits and follow-ups

The check's grant is scoped to its own bridge connection, which ends with the check, so a real client with the same label still meets the prompt. The check's released value arrives in the app process, which already holds the vault, and is read in place and zeroed; the operating system's pipe buffers are not.

The app, like `setup`, runs whatever `claude` or `codex` comes first on PATH, and registers the first `keypaste-mcp` on PATH when none is beside it. A same-user program that can change PATH can already reach the vault's endpoint, so this gives it nothing new.

On Windows a client installed only as an npm `.cmd` shim is not found, because the runner starts executables without a shell. That is `setup`'s existing behaviour.

A moved or deleted `.AppImage` leaves the client's registration pointing at nothing until the person connects again. Nothing in the app notices.

The app does not read a client's configuration, so it cannot say whether a client is already connected. It shows what the last action did in this screen. Codex, Cursor and Claude Desktop were not observed from the app, and neither was Linux with a real client.

A person's rendered review of the section is outstanding; check 48 in [desktop.md](../desktop.md) covers it.

Two defects surfaced in CI while this step ran, and neither is repaired here. F.17's `DrawnMaskTests` exposure recurred four times. Its row now records those runs and the mechanism to test first: the one-character value is always `Q`, and on Linux the fixture's temporary directory name holds six random characters from `[A-Za-z0-9]`, which the shell's vault-path tooltip shows. The Approve timeout in `DesktopApprovalTests` is new, and [STEPS](../STEPS.md) has F.18 to diagnose it.
