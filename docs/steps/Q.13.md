# Q.13 — Take files by drag and from the system

Completed 2026-11-05 on `q13-files-by-drag`, Implemented in source and built into each package by a dispatched `app` run; no package was installed.

## Amendments

Settled in the step, all reversible:

- **The file's kind decides, not where it lands.** The row says "dropped anywhere", so a KeePass file or an export imports and a `.env` goes to its project wherever it is dropped, and any other file attaches to the open item. A `.kdbx` or `.env` is therefore attached only by the pane's Add, whose picker takes anything. The frame goes round the pane for an attachment and round the content for an import, and the caption says which before the release.
- A `.env` goes to the project in view, or the first, as Import .env does, through the discard question. With no project it is not taken, since the new-project form could not keep the file. `.env.keypaste` holds references, so it is not taken as one.
- One file at a time, as a picker gives. A drop goes nowhere while an import, a question, Share, the generator or a YubiKey wait is up, or an agent's prompt waits. An attachment goes nowhere during an edit or with any draft on the screen, a typed group name included, and a KeePass file or an export opens its preview over a draft, as its menu command does. Nothing lights for a drop that would be refused: over the 5 MiB cap, named like an attachment the item has, or onto a group core's `Vault.RelocationRefusal` says would refuse the item; a drop of the first two says why in a toast.
- On the unlock screen a drop takes a vault, or a damaged path with backups beside it, as the picker's `Offer` does, and only while the opening form is showing and idle. A password typed for the vault selected before is zeroed when the selection changes.
- **A platform may not name the file until the drop.** The effect then allows the drop with nothing lit, and the drop is judged there: the shell says so in a toast, the unlock screen in its line.
- **An item's drag holds the item in the process.** The platform has to be given something, so it gets one constant byte in an application format. Foreign drags carrying that format move nothing, since only `ShellView`'s own `DoDragDropAsync` holds an item. It moves onto groups only: the top level is not a group, and Rename or move… reaches it. Touch does not start a drag, since a finger scrolls.
- **On the rail** no group is on screen, and a press outside closes the overlay, so it could not be opened first. Holding an item on the groups button for 500 ms opens the overlay, a drop on a group moves the item, and the drag's end closes the overlay wherever it ended. With the sidebar hidden there is no target, and Rename or move… remains.
- **The pipe now carries a line.** This reverses T-29's "the connection is the whole request". A start sends one line, empty or a full path, while reading its reply, so an app of an earlier version that never reads costs it nothing; a start of an earlier version that sends nothing is answered after the one-second read bound. Over 8 KiB, invalid UTF-8, a path not fully qualified or one holding a control character names nothing and still shows the window.
- **A vault open asks.** "Lock … and open …?" is a new dialog with Cancel focused and a neutral action. It departs from DESIGN's rule that Return answers with the action, because something other than the person can raise it. A draft goes on to the discard question. It holds the menus as any dialog does, and Cancel returns focus to where it was. A file the unlock screen would refuse never reaches it: a network location, the open vault itself, or one that isn't a readable vault gets a toast with the vault left open, so a damaged vault with backups can be restored from there only after locking by hand. While another dialog is up, a toast says the file was left, and nothing queues.
- A handed file on the unlock screen with a password typed, a form open or an unlock running is not selected and not queued; the line says so. A file keypaste has not opened shows its full path, since a same-user process could offer a file named like the person's vault: in Fragment Mono under the heading rather than the message line, so typing does not clear it, with every invisible character escaped, on the restore branch too.
- A handed path on Windows that does not start at a drive letter, itself or after `\\?\`, is refused unread, since touching a server sends credentials to it, a link to a `.kdbx` could choose that server, and Windows has more spellings of one than can be listed. The picker and a drop still take one. This is beyond the row and is the founder's to reverse.
- A FIFO, socket or device would hang the UI thread in the header read, so `HandedFile.IsWholeFile` requires a length, behind links too, and `KdbxHeader.IsVaultFile` asks it first, which covers the picker, the restore form and every other caller.
- `SelectedName`, the shell's `VaultName`, the recent lists and the File menu's recent vaults now go through the display sanitizer, so a right-to-left override in a file name cannot draw there, and each file's tooltip shows its path with every invisible character escaped.
- The recent list kept showing the old row as selected after any selection outside it, the picker's included: `SelectedPath` did not notify `SelectedRecent`. Found in frame `d2`, fixed and held by a test.
- Windows registers `keypaste.Vault` and `.kdbx\OpenWithProgids` as plain registry values, because WiX's `Extension` element writes the extension's default and would take it from KeePassXC. Linux names `application/x-keepass2` and takes `%f`. macOS declares `kdbx` with role Editor and rank Alternate by extension, importing no UTI.
- The frame is `KpTextSecondary` and the caption a toast, so no view gains an amber. `D-` labels went from the source files touched where they were not the row's own reference.

## Limits and follow-ups

- Avalonia's own drag sources and targets on macOS (`AvaloniaNativeDragSource`), Windows (OLE) and X11 (`X11DragSource`, XDND) were not exercised, nor `FileActivatedEventArgs` from `application:openFiles:`. That the macOS event arrives after `Launch` subscribes, and that a file is nameable during the drag on each platform, are read from how they work, not observed. A Wayland session under XWayland is unchecked.
- An AppImage's `.desktop` reaches a file manager only through a desktop integration tool; a bare AppImage registers nothing.
- The window's 40-pixel drag strip on the unlock screen does not take a drop, since it must stay the window's move handle.
- The checklist in the [desktop guide](../desktop.md) now holds the acts that need real machines.
