# 4.11b — Receive crash reports at keypaste.com, switched off

Completed 2026-10-28 on `t6-crash-site`, source only; runs pending.

## Amendments

The founder approved the design's recommendations on 2026-10-28: D1 as the store, 90 days' retention with Workers invocation logs off, a `CRASH_ENABLED` flag keeping the route off on `main`, no third-party service, and only packaged builds sending. Later that day the founder accepted the choices below, kept the cap at 200, had the reader script built, and chose Cloudflare's default location for the database, with no EU jurisdiction (D-0588). Where the design left detail open:

- **A row's failure.** The design's fingerprint, the kind, the exception type and the first eight frames' names, also takes the catch site, so two catch-everything blocks that catch one exception keep separate rows (D-0587).
- **The daily cap.** The design put a daily cap on new rows behind the rate limit without a number. It is 200 new rows a day, which keeps the table under 300 MB even if every row held a 16 KiB report for 91 days, within D1's 500 MB limit for a database on the free plan ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)); a repeat of a row always counts (D-0587).
- **The node tests' place in CI.** The design put `npm test` in `verify.sh`'s scripts profile; it is a step in ci's checks job instead, as D-0475 placed the Claude Desktop extension's, so it runs once on Linux and the scripts profile, which a contributor's full `verify.sh` run also runs, gains no Node and npm prerequisite (D-0589).

## What changed

- **The route.** `site/src/crash.js` answers `POST /api/crash`, routed from `worker.js` (D-0586). It mirrors `CrashScrubber.TryRead`: each field's grammar rule for rule, then the report written again in the scrubber's field order and compact form, which must equal the bytes received, and again with the largest count, which must stay within 16 KiB. So an exception message, a frame's file, a field the scrubber does not write, another order or spacing, a byte order mark and invalid UTF-8 are all refused. The checks run in the order switch, method, origin, `CRASH_LIMIT`, content type, size and shape, and only a report that passes them reaches D1.
- **Storage.** `site/crash-schema.sql` makes the one table and its two indexes. One statement adds a report to its row or, while fewer than 200 rows were first seen today, makes a new one, so the cap and the merge cannot race. The `*/30` cron that sweeps shares also deletes rows last seen more than 90 days ago, whenever `CRASH_DB` is bound, the route on or not (D-0587).
- **Switched off.** `wrangler.jsonc` gains the `CRASH_LIMIT` binding (10 a minute, namespace 1003) and no D1 binding or `CRASH_ENABLED`, so the next deploy from `main` needs no database and the route answers 503 with `retry-after: 86400` (D-0588). `site/README.md`'s Crash reports section gives H-0028's steps: create the database, add the binding and the flag, apply the schema, integrate the commit, then check the refusals and a probe report.
- **Invocation logs off.** `observability.logs.invocation_logs` is `false`, so Cloudflare's Workers Logs keeps no record of each request to any route of the site Worker: crash reports, the share routes and `/subscribe` alike. The Worker's own console lines, which name an error's name and message only, are still kept (D-0587).
- **CI.** ci's checks job installs the site's runtime dependency, `postgres`, without its dev dependencies or install scripts, and runs `npm test`, so the share tests T-33 cites run in CI for the first time; `site/test/*.mjs` no longer skips ci on `main` (D-0589). `share-api.test.mjs`'s sweep test now waits for both of the cron's sweeps.
- **The reader.** `scripts/crash-reports.sh` runs on the founder's machine through the site's pinned Wrangler with `d1 execute --remote --json`: by default it groups the rows last seen in 90 days by fingerprint, summing failures and listing versions, platforms, kind, catch site, exception type and top frame; `--days`, `--version` and `--show <fingerprint>` narrow it. Its queries are fixed selects, and each argument must fit a grammar with no quote before it reaches the SQL. It refuses to run before `wrangler.jsonc` binds `CRASH_DB`, has no `--selftest` because it guards no release path, and joins the scripts the `workflows` profile shellchecks (D-0587).
- **The manual check.** `verify-site-endpoint.sh` reads whether `wrangler.jsonc` sets `CRASH_ENABLED`: while it does not, the live route must answer 503 with `retry-after: 86400`; once it does, it must refuse a body that is not a report (400), one that is not JSON (400), a foreign origin (403), an oversized body (413) and a GET (405). No request it sends is a report the route would store.

## Evidence

Nothing was built, installed or run on this machine but `bash -n` on `verify-site-endpoint.sh` and `crash-reports.sh`; no .NET code changed. `crash-reports.sh` cannot run before H-0028 makes the database, so its queries and its reading of Wrangler's `--json` output are untried. `site/test/crash-api.test.mjs` runs under `node --test` with a D1 stand-in over `node:sqlite` that loads `crash-schema.sql`, so the route's SQL runs against the schema H-0028 applies:

- the vector reads back as `JSON.stringify` writes it, which the tests' changed reports rely on;
- with `CRASH_ENABLED` unset, `"0"` or `"true"`, or with no `CRASH_DB`, a POST and a GET answer 503 with `retry-after: 86400` and nothing is stored;
- each vector report is stored as sent, in a row with only the schema's columns, today's dates and nothing of the sender's address;
- a repeat with other offsets, OS version, screen, uptime, date and inner exceptions adds its count to the first report's row, and another version, OS, architecture, kind, exception type, frame name or catch site makes its own;
- 44 bodies are refused with 400 and leave the table empty, among them an exception's and an inner exception's message, an added field, another order, spacing, a trailing newline, a byte order mark, invalid UTF-8 and a bad value for each field and frame rule;
- a 16,375-byte report is taken, a 16,376-byte one, which a merged count would take past 16 KiB, is refused with 400, and a 16,385-byte body with 413;
- a foreign `Origin` answers 403, and keypaste.com's is taken;
- PUT, GET and DELETE answer 405 with `allow: POST`, and a path below `/api/crash` 404;
- `CRASH_LIMIT` is asked with the sender's address, and its refusal answers 429 with `retry-after: 60`;
- with 200 rows first seen today a new failure answers 503 with a `retry-after` within a day while a repeat still counts, and the next day's first new failure is stored;
- the cron, with the route off, deletes a row last seen 91 days ago and keeps one last seen 90 days ago and one today;
- a D1 failure answers 503 with no `retry-after` and logs one line holding nothing of the report or the sender;
- every answer carries `cache-control: no-store`, `referrer-policy: no-referrer` and `x-content-type-options: nosniff`.

Cloudflare's documentation, read 2026-10-28, gives `observability.logs.invocation_logs = false` ([Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)) and says a binding with no resource ID has the deploy create the resource, D1 included, with deploys from the dashboard or Git as well ([Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/)); the [changelog of 2025-10-24](https://developers.cloudflare.com/changelog/2025-10-24-automatic-resource-provisioning/) dates this to Wrangler 4.45.0. The site pins Wrangler 4.114.0.

Runs: pending, in the batch's ci run, whose checks job runs the node tests; no `dev.sh` mode runs that job alone.

## Decisions

D-0586 (the route), D-0587 (what is kept and for how long), D-0588 (off until H-0028) and D-0589 (the node tests in CI). THREATS T-9 says what the route keeps and that anyone can forge a report.

## Limits and follow-ups

- The live route's 503 waits for the deploy of the commit that integrates this step and a run of `verify-site-endpoint.sh` by hand; H-0028's row carries it with the probe that follows switching it on.
- Invocation logs off covers Workers Logs only. Cloudflare's own analytics and security events for the zone, and a `wrangler tail` someone runs, are not changed by it.
- D1's Time Travel can restore a deleted row for up to 30 days on the paid plan, 7 on the free one, so a report can outlive the 90 days by that much; the draft terms say so.
- What `wrangler deploy` does with a D1 binding whose database does not exist was not found in Cloudflare's documentation and was not tried; the design avoids the question.
- The rate limit counts per Cloudflare location and approximately, so many addresses or locations can pass it; the daily cap bounds the rows they can make, not the repeats they can add.
- No memory store serves the route: 4.11c's `verify-crash-report.sh` can run the Worker under `wrangler dev` with a local D1 binding and the schema applied with `wrangler d1 execute --local`.
- The database's default location and no jurisdiction cannot change after H-0028 creates it; moving it means a new database.
