# 9.2b — Use TOTP in the app and approval bridge

Completed 2026-10-21 on `main` at `2073f24`, source only: ci 39646134010 and app 39646133940, every job green.

## Amendments

The row asked for the code and its countdown in the app, and for an agent to be approved for a code but never for the seed. The founder's plan of 2026-10-21 set its shape: the app shows an item's current code and countdown with copy, following the entry pane's patterns, and leaves the seed field as it is; an agent asks for the current code under `request_credential`'s approval, the owner computes it so the bridge stays vault-free, the audit line records the item and that a code was released, and the seed fields are never releasable by name; protocol version 2 is kept if possible. Each choice that shape left open was taken as recommended, under the decision rule of 2026-10-21 the task carried, and is founder-delegated:

- **A field mode, not a new tool.** `request_credential` takes `field: totp` (D-0480). It reuses the request's validation, the reach re-check, the values setting, the cooldown, Automatic, the prompt and the owner's line unchanged, so no tool, audit method, message kind or protocol field was added and the version stays 2. `totp` is lower-case, so no custom field that leaves by name can be called that. A newer bridge talking to an older owner is refused as an invalid field, and an older bridge refuses `totp` itself.
- **Once, never a timed allowance.** A grant serves the value it released, and a code is stale when its period ends, so the prompt offers Allow once only and says why (`OnceOnly.TotpCode`), and nothing is put in the grant cache. A person's answer or the agent's Automatic mode releases each code. Recomputing a code from a grant would make the grant a standing capability, which `GrantCache` exists to avoid.
- **The code's lifetime is its seconds left.** The reply, the tool's `expires_in_seconds` and the line's `granted_seconds` carry the whole seconds until the next code, rounded up, in place of the agent's `ttl_seconds` or an allowance's length. The source returns it on `ReleasedField.CurrentFor`.
- **Reach.** A project tag's reach covers only the item's variables, so a code is reached only through an item's place, as the password is.
- **Listing.** `list_entry_names` names `totp` after the standard fields for an item whose `otp` or a KeePass 2 secret field holds anything, judged by the length KeePassLib keeps, so no value is read. A malformed one is listed and refused once asked.
- **No TOTP.** An item with none keypaste can compute is refused after the yes, when the code would be read, as `failed` with "the item has no TOTP keypaste can compute" (`CredentialFailure.NoCode`), as an empty field is.
- **The seed by name.** `otp` and `TimeOtp-*` already failed the environment-variable rule; `CredentialFields.IsCustom` now also refuses every field a TOTP is read from, so a later change to that rule cannot let one leave through `request_credential`, a `kp://` reference, `share` or `{S:…}`.
- **Refusal text.** The fixed refusal for a field a request may not name now lists `totp` (`CredentialFields.RequestRule`), so `verify-approval-e2e.sh`, `verify-desktop-approval.sh` and `verify-keepassxc-fields.sh` expect the new words; `CredentialFields.Rule`, which `kp://` references and shares use, is unchanged.
- **Masked in the app** (D-0481). The code is a credential for as long as it is current and a screen share would carry it, and the design rules keep a secret masked until revealed, so it is masked like the password: Reveal shows it while held and Copy puts it through the clearing countdown as `TOTP code`. The countdown is always visible.

## What changed

Core: `TotpSpec.Remaining` gives the time left from the period alone and `TotpSpec.MayHold` judges by name and length; `Vault.ReadSavedTotp` reads the TOTP only while the vault matches its file (D-0317); `VaultCredentialSource` takes the session's clock and, for `totp`, computes the code after the entry is found, disposing the spec before it returns; `ApproverHandler` offers no timed grant for a code and carries its lifetime. `SessionServer` passes its clock to the source.

Bridge: the schema's field enum gains `totp`, its descriptions and the tool's say what it is and that a code lasts only until it changes.

Approvers: the app's prompt says "once only: a TOTP code changes every period" and `keypaste approve` "a TOTP code changes every period: no timed allowance is offered."

App: `EntryTotpRow` is the pane's TOTP row, a mask as wide as the code with the seconds until the next code from a one-second timer on the session's clock, posted to the UI thread through the shell's `post`, which `EntriesViewModel` now passes on. A TOTP keypaste refuses shows the refusal in its place.

## Decisions

- D-0480: `totp` in `request_credential`, released once or under Automatic for its seconds left, computed by the owner, and the seed fields refused by name.
- D-0481: the entry pane's masked code, countdown and copy.

## Limits and follow-ups

- A code held across the end of its period is read again from the vault when the countdown finds the new period, so the hold shows the new code within a second of it starting (gaps-1, RUNS-PENDING).
- `verify-keepassxc-fields.sh` compares `keypaste get <item> totp` with `keepassxc-cli show --totp` for every form KeePassXC reads, Steam included, within one period and once more when a pair straddles a period's end (gaps-1, RUNS-PENDING).
- A code is a second factor: an agent allowed the password and the code can sign in as the person within that period, and keypaste cannot see where either is used. Each is still a separate release with its own line.
- A malformed `otp` is listed to agents as `totp` and refused only once asked and allowed, so a person can be asked for a code that then is not released.
- `keypaste get <item> totp` gives the current code under `get`'s reveal rule, never the seed, and `keypaste show` lists `totp` with no value beside `otp` and `TimeOtp-*`, masked as before (D-0497) (gaps-1, RUNS-PENDING).
