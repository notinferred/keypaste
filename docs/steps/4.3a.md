# 4.3a — Attach MCP to the shared session

Completed 2026-09-23 on `main` above `61bae2e`, source only. [PRODUCT](../PRODUCT.md) and [STEPS](../STEPS.md) own scope and the plan; this record is what the step did and is not revised afterwards.

## Scope as selected

**Build:** every `keypaste-mcp` request reaches the session authority U.1 establishes over its authenticated per-user endpoint, and the authority answers it through the existing approval gate. One field per release, the requested scope and TTL, the exposure rules and the protocol's size and shape limits are enforced where the vault is held, not in the bridge. A request that reaches a locked, absent or different session, or whose attachment fails, is denied and audited as a denial. The bridge never opens a vault or asks for a master password. Traces to PRODUCT §§2 and 3.2, 3.3 and 3.7.

**Verify (V-4.3a):** a real MCP client's request through `keypaste-mcp` reaches the owning session and is answered by its gate, and the audit record names that session. An unexposed entry, a second field, a TTL over the limit and a malformed request are each refused by the authority, with the bridge unchanged. The same request with the app locked, with no owner running, against a stale session identifier and with an invalid attachment each denies and writes a denial record. A listener that only accepts a connection, or a check made only in the bridge, does not pass.

The founder approved the plan as written; there was no amendment.

## What changed for users

U.1 to 4.4b had already done most of this. Every bridge request attached to the owner's session, the owner refused unattached, other-vault, ended-session and locked requests, and the bridge audited those as denials. The owner re-checked the field and the exposure after resolving a handle. What this step changes:

- **The owner applies every argument limit itself (D-0324).** Only the bridge refused an `entry` of 0 or more than 512 characters, a `reason` of 0 or more than 2000, and a `ttl_seconds` outside 1 to 3600. The owner, whether the app or `keypaste agent`, now refuses each as `invalid-request` before it resolves, reads or asks anything. The rule is one core function, `Core/Approval/CredentialRequestRules.cs`, and the bridge uses it too, so what agents are told is unchanged word for word. The owner used to clamp an out-of-range TTL, so a direct request for two hours was asked about as five minutes. It is now refused. A TTL inside the range is still clamped to `--max-ttl` and to a rule's ceiling, as before.
- **A frame that names a property twice is not read (D-0325).** A credential request carrying `field` twice used to be read as whichever came last. It now ends the connection unanswered, like any other unreadable frame, and so does a reply that names its value twice.
- **Nothing changes for an agent using the shipped bridge.** Its own checks refuse these requests first, with the same text as before. What changed is that a process speaking the approver protocol directly, which THREATS.md T-10 confines to the same user account, now meets the same limits as the agent.

## Evidence

**Tests**, over real pipes:

- `SessionAuthorityTests`, 16 new, with the fixture's person set to approve anything, so a missing check would release:
  - Ten requests outside the limits are each refused as `invalid-request`, naming the argument, with no value, nobody asked and nothing read. They are an empty and a 513-character entry, fields `password,username` and `totp`, an empty and a 2001-character reason, and TTLs of 0, −5, 3601 and `int.MaxValue`.
  - A 3600-second request is still granted, at the owner's 300-second ceiling.
  - An unexposed entry, by path and by handle, is refused as `out-of-scope`, unasked and unread.
  - Over a raw pipe after a real attachment, a frame naming `field` twice, one with `field` as a list and one with no `ttl_seconds` each end the connection unanswered, with nobody asked.
- `ApproverProtocolTests`, 2 new: a request naming `field` twice and a reply naming `value` twice do not decode.
- `OwnerDenialTests`, 5, new: the shipped bridge's tools against a real `SessionAuthority` over a real vault, whose person approves anything.
  - The approved request returns the value, and its audit line names the owner's session.
  - A locked owner is audited as `vault-locked`.
  - No owner is audited as `no-approver`.
  - An owner holding another vault is audited as `no-session`.
  - For the stale session, the owner locks and unlocks while the first request's reply is lost. The bridge's retry under the first session is refused and audited as `no-session`.
  - Each denial writes exactly one line with no session. The value is in neither the log nor the wire, and nobody was asked.
- `ServerToolsTests`, 1 new: the tool schema's bounds equal the core rule's.
- `BridgeSourceRulesTests`, 1, new: no file under `src/Keypaste.Mcp` names a way to open, create or unlock a vault or read a password.

**Gate**, [verify-approval-e2e.sh](../../scripts/verify-approval-e2e.sh). It now reads the session from `keypaste agent`'s `listening on` line, and requires that the request made with no agent running is audited as `no-approver` with no session. It also requires that the approval and the refusal are both audited as `prompt` under that session. It passed locally on Windows 10. [verify-session-authority.sh](../../scripts/verify-session-authority.sh) and [verify-session-lifecycle.sh](../../scripts/verify-session-lifecycle.sh) already prove the app's side unchanged. A real `keypaste-mcp` request is answered by the app's gate, and its audit line names the app's session. Locked, quit, killed and relaunched owners are each audited as denials reaching no session.

## Limits and follow-ups

The app's gate still has nowhere to ask a person (D-0311), so through the app a valid request is answered by that gate as a refusal; approving in the app is 4.4. The approved path through a real gate across processes is `keypaste agent`'s, in the approval gate.

The stale-session case needs a lost reply, which the shipped bridge produces only when the owner's connection dies mid-request. The test forces that loss inside the owner rather than killing a process, so the gate does not reach this case.

An unknown property in a frame is still ignored rather than refused, so that an optional field can be added without a version bump, as `ApproverProtocol.Version` says. Only the named properties are read, so an extra `fields` list cannot widen a release.

A process speaking the protocol directly still writes no audit record (T-10), and it chooses the exposure it sends. The owner checks that exposure's form, not whether it matches any client's configuration.
