# 8.1c — Answer the browser from a vault-free relay

Completed 2026-10-29 on `t6-relay`, source only; runs pending.

## Amendments

- **The database hash.** The row names no answer to `get-databasehash`, and the hash keypaste answers is 8.1d's, from the owner. Until then the relay answers it with error 1 while nothing holds the vault unlocked and error 2, "Database hash not available", while an owner is unlocked, so the extension never offers to pair (D-0627).
- **One more nonce refused.** The row refuses a request nonce already seen and one equal to a reply nonce. The relay also refuses a request whose reply would be sealed under a nonce the session used, since a box key is the same in both directions; a key exchange under a used nonce is answered with error 9, and a sealed request before any key exchange with KeePassXC's error 3 rather than 4 (D-0625).
- **Both ways apart.** The owner admits pairing, check, fill and lock only on a browser's attachment, as the row says, and a browser's attachment makes nothing else, as the design's architecture says (D-0627).
- **The seam for 8.1d and 8.3a2** is `Core/Browser/IBrowserRequests.cs`, which the app and `keypaste approve` are not yet given, so they refuse every pairing, check and fill, and record none of them until 8.1d's browser kind of audit line (D-0627).
- **The fake browser** seals with the libsodium box `Keypaste.Browser` calls, through that project's internals, so `SodiumSourceRulesTests` allows it to reference the project; that the box is the one TweetNaCl.js seals is held by 8.1b's known answers. `Keypaste.Browser` now references Core for the pipe and the vault's location (D-0624).

## What changed

- **The dispatch** (D-0624). `Program.cs` hands a browser's start to `BrowserEntry.RunAsync` after the bridge and before `--selftest` and the verbs, decided by `BrowserEntry.StartsRelay` from the arguments alone: a Chrome-family origin, with `--parent-window=<n>` on Windows, or Firefox's manifest path and add-on ID (`BrowserCaller.cs`). The relay answers only the three callers `Core/Browser/BrowserIdentity.cs` names, and any other, or a malformed `KEYPASTE_APPROVER`, exits 1 before standard input is opened.
- **The relay** (`src/Keypaste.Browser/Relay.cs`, D-0625 to D-0628). It finds the vault's owner as `keypaste mcp` with no arguments does (`RelayOptions.cs`), frames messages in native byte order and refuses one over 1 MiB (`NativeMessages.cs`), makes a fresh key pair at each key exchange, keeps the session's nonces (`NonceLedger.cs`), answers each refused action with KeePassXC's code, reports version 2.6.0, sends the owner only typed requests, with a fill only the pairing the last check proved, and seals its answers under the request's nonce incremented. It sends `database-locked` when the owner ends its link and `database-unlocked` on the first request that attaches after, knocks on the locked app's pipe on `triggerUnlock`, writes no audit line, and exits when standard input closes or on SIGTERM.
- **The pipe** (D-0627). The attach request gains `browser`, and the protocol `browser-pair`, `browser-check`, `browser-fill` and `browser-lock` with their replies (`ApproverProtocol.Browser.cs`, `BrowserMessages.cs`). `SessionAuthority` admits them only on a browser's attachment and nothing else on one, locks for a browser as `keypaste lock` does, and hands the other three to an `IBrowserRequests`, releasing a fill's logins only while their unlock is live and within one frame. `Core/Ipc/BrowserLink.cs` is the relay's connection, with a read always pending between exchanges; `ApproverClient`'s connect is shared with it.
- **`tests/Keypaste.FakeBrowser`**, in `keypaste.slnx`: `ExtensionClient` speaks the extension's protocol to a host's standard input and output, and its program starts a host with each browser's arguments.
- **Records.** ARCHITECTURE gains the relay, its process and request path, and the fake browser; THREATS widens its title to browser fill and gains T-48.

## Limits and follow-ups

- **Nothing pairs or fills yet.** The app and `keypaste approve` refuse every pairing, check and fill, unrecorded, and the relay answers `get-databasehash` with error 2 while an owner is unlocked; 8.1d builds pairing, the hash and the browser kind of audit line, and 8.3a2 the fill.
- **No browser starts it.** Nothing installs the manifest until 8.1e; the fake browser's program, which starts a host as each browser does, is first driven by 8.1d's `verify-browser-host.sh`, and real browsers by 8.3a3. The relay's tests run it in their own process, so SIGTERM and a Windows job object ending it are untested.
- **One message at a time.** The relay reads the browser's next message only once the one before has its answer, and notices standard input closing only between messages, which 8.3a2's fill, waiting on a person, must take into account.
- **Released strings stay.** The usernames and passwords the relay decodes from the owner's reply are strings it cannot zero (T-48).
- **Each request with nothing listening** waits the bridge's 500 ms to connect before it is answered with error 1.
- **The relay uses the default `KEYPASTE_HOME`** unless the browser was started with another, since a browser passes its host its own environment.
- **Error words** are KeePassXC's English, which the extension shows as sent.
- The NativeAOT `keypaste`, its trim analysis and `--selftest`, are built only by the batch's full run.
