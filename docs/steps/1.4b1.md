## What changed

- **The base** (D-0538, D-0599). `KeePassInterop.TakeBase` keeps each group's and entry's parent, `LocationChanged`, keyed content digest and whether it was in the recycle bin, and the tombstones, with no plaintext. `Vault` takes it when it is made and after each save.
- **The merge.** `Vault.MergeInto(file, out report)`, internal, merges the open copy into `file`, a fresh open of the vault's file, which becomes the result: unsaved when it took anything from the open copy, and saved under the stale-write check against the file it was opened from. `KeePassInterop.MergeFrom` builds it inside that parse, reading the open copy and never changing it. Entries and groups are matched by UUID across the whole tree. An entry with equal content is the file's; a change only the open copy made is its; one only the file made is the file's when the base's version is in its history; otherwise the later in whole seconds is current, and a tie is the open copy's, stamped a second after every version and deletion it competes with. Histories are both copies' versions and the one displaced, a version of the same second and content held once, ordered by time and trimmed to the vault's limits only where the merge added a version, never the displaced one, which carries a mark so KeePassLib's trimming spares it too until the entry's next edit (D-0601). Places, recycling, restores, tombstones, groups, the two bins, custom icons, meta and header follow D-0537 to D-0541; an object kept against a deletion keeps the version it was in its history (D-0600).
- **KeePassLib** (`KEYPASTE_KEPT_VERSIONS`). `PwEntry`'s history maintenance, which every load, save and backup runs, removes the oldest version without the `KEYPASTE_KEPT_BY_MERGE` mark and stops when only marked ones are over the limits, and `CreateBackup` removes the marks first; without a mark it trims as upstream does.
- **The report** (D-0603). `VaultMergeReport`, in `VaultMerge.cs`, says whether the result took anything from the open copy and names, never by value, the items changed in both copies with which is current, those kept against a deletion with which copy deleted them and whether they are in the bin, the groups changed in both under different names with the name each lost, and the agents whose records changed. `VaultMergeOutcome` names the refusals.

## Limits and follow-ups

- **No front end merges yet.** 1.4b2 reads the file once, refuses a file below KDBX 4, merges through `MergeInto` and saves; 1.4b3 and 1.4b4 call it from the owners; 1.4b5 applies the token rule.
- **KeePassXC trims on its own saves**, so a version kept past the history limit lasts there until KeePassXC next saves that item (D-0601). The mark is entry custom data on the history version, which KeePassXC keeps and may show among an entry's plugin data.
- **A change only the file made, stamped before the base, is not stamped.** It is taken by lineage against the stamps, and D-0539 stamps only a tie's winner and an object kept against a deletion, so a later time-based merge with the open copy's older file, KeePass's or KeePassXC's, makes the open copy's version current again with the file's in history. The convergence case leaves it out.
- **The open copy's bin stays as an empty group** when the copies name different bins: its contents move into the file's bin, and the group, no longer the bin, is listed as an ordinary group, as KeePass's synchronize also leaves it.
- An object the open copy adds is appended to its group; sibling order is otherwise the file's, and KeePass's reordering is not reproduced.
- Custom data's own times are not compared, since KeePassLib keeps them internal (D-0599).
