# 1.4a — Specify merge and deletion semantics

Completed 2026-10-24, documentation only; founder approval 2026-10-24.

## Amendments

None. The founder approved the specification with each of its fourteen decisions as recommended.

## Evidence

Research only, from `43debae3` on `t6`: the vendored KeePassLib 2.61, KeePassXC 2.7.6 and 2.8.0 (`src/core/Merger.cpp`, `src/core/Group.cpp`, `src/gui/DatabaseWidget.cpp`, `src/cli/Merge.cpp`, `tests/TestMerge.cpp`) and keepass.info's synchronization help. Nothing was built or run.

**keypaste.** Three findings went beyond the row. Only the desktop's own edits can be left unsaved: a terminal's edit and a change to an agent's settings are taken back when their save fails (`AppVaultSession.cs`, `SessionEditor.cs`), so `keypaste approve` never holds an unsaved change. `Vault.Checkpoint` and `Restore` put back entries with their attachments, group times, tombstones and the recycle-bin pointer, but not group names, group parents or the database's meta, all of which a merge can change. Revoking a token deletes and purges its record, leaving only a tombstone (`TokenStore.cs`), which KeePassXC's default merge does not honour. Core never calls `PwDatabase.MergeIn`; one test does, to show two copies' agents' records converge (`AgentAccessStoreTests`).

**KeePass 2 and KeePassXC.** Both match objects by UUID and merge whole entry versions, the newer current and the older in its history; KeePass's help gives a user name and password staying a consistent pair as the reason. They lose data or differ here:

| Case | KeePass 2, `MergeIn(Synchronize)` | KeePassXC 2.7.6 and 2.8.0, default mode |
|---|---|---|
| Both changed in one second | The source's version replaces the target's and neither is kept (`PwEntry.cs:495`, `PwDatabase.cs:881-893`) | The target's is kept and the source's current version dropped with a log warning (`Merger.cpp:542-566`) |
| History | Versions sharing a time collapse to one (`PwDatabase.cs:1662`) | One version per second (`Merger.cpp:508-538`), the cause [F.27](F.27.md) found |
| History limits | Every entry is trimmed after a merge (`PwDatabase.cs:939`) | The merged entry is trimmed (`Merger.cpp:598`) |
| Deletions | Applied when the object is older than the tombstone, an entry going with its whole history (`PwDatabase.cs:1066-1118`) | None applied: the default mode is KeepNewer (`Group.cpp:207`) and deletions run only under Synchronize (`Merger.cpp:610-614`), so a merge with any copy still holding a deleted entry brings it back, as KeePassXC's own test asserts (`TestMerge.cpp:1187-1223`) |
| Moves | The later `LocationChanged` wins | The same, but the other copy's older `LocationChanged` comes with its winning content (`TestMerge.cpp:886-935`) |
| Group fields | The newer whole group, custom data included | Name, notes, icon and expiry from the newer; custom data, tags and flags never (`Merger.cpp:264-329`) |
| Database meta | Each field by its own changed time (`PwDatabase.cs:1541-1633`) | The target's, its custom data replaced when the source's is newer; the recycle bin and name not merged (`Merger.cpp:700-765`) |
| Another database | Its root added as a subgroup (`PwDatabase.cs:789-822`) | Its contents merged into the root |
| The source copy | Changed: backups are added to its entries (`PwDatabase.cs:886`) | Read only |

KeePassXC's window, finding the file changed while it holds unsaved changes, asks Merge, Ignore or Discard and merges the open database into a fresh copy of the file (`DatabaseWidget.cpp:2213`); with nothing unsaved it reloads without asking, since AutoReloadOnChange and AutoSaveAfterEveryChange default to on. `keepassxc-cli merge A B` merges B into A, so `merge -s` with the file as target and the open copy as source is the gate's oracle.

## Limits and follow-ups

- 1.4b is built as its children 1.4b1 to 1.4b5 in STEPS and keeps its place in ROADMAP's 1.0.0 row.
- Whether KeePassXC 2.7.6 and 2.8.0 keep a version intact across their own load and save is unmeasured. If a round trip changes a version's digest, lineage cannot be shown and the time rule decides, as in KeePassXC; 1.4b3's gate case G3 measures it.
- A group changed in both copies loses the older copy's notes, since KDBX keeps no group history. The notice names the group; whether that is enough is the founder's to say.
- An item open in the editor during a merge is left as typed, so a field the other program changed in it is replaced at its next write and kept in history. Whether the editor should first say the item changed is open.
- With lineage unknown and the other computer's clock behind, its newer edit goes into history and the notice names it; nothing better is possible without lineage.
- KeePassLib drops XML elements it does not know on every save. A merge drops nothing more, but it writes where a reload would not have.
- Other programs' merges stay outside keypaste: KeePassXC's default merge on another computer still brings deleted entries back and keeps one version per second. T-15 and T-32 say so when 1.4b3 and 1.4b5 ship.
- X.10 needs 1.4b. Whether a copy the relay delivers needs anything beyond these rules is not decided.
- THREATS, SECURITY, the guides and D-0317 describe what is built, so they change with the children. No CHANGELOG entry, since nothing users see changed.
