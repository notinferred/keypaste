## Decisions

Settled in the step, all reversible:

- **Prompt activation.** Each activation disarms the allows, starts focus on Deny and arms them a second later. Losing focus disarms them and cancels any wait, and a wait that ends without focus arms nothing, so a bring-forward the system refuses, as Windows can, stays disarmed rather than arming early. A prompt that opens without focus is disarmed until a press activates it: the press that activates lands on disarmed allows. Deny works at any time, so a prompt is always answerable; an allow takes activation and a second. It is drawn inactive from the moment it opens without focus, since such a window raises no `Deactivated`. Drawn inactive means colour alone, a quieter border, title, tile and shadow, so the fixed layout does not move and every label stays readable. `Window.IsActive` is the one input, read on the UI thread. **A platform that never reports activation would leave a prompt unanswerable but for Deny**; a real desktop reports it, and the checks below are headless, so this is the step's largest unobserved risk, and T-11 and the approvals guide say so. An X server with no window manager is such a platform, and the acts run under openbox.
- **The driver and the acts.** `exercise-desktop-acts.sh` now activates the prompt before pressing Allow once. It also dropped `invoke Delete` after `id:DeleteEntry`, a confirmation that Q.5 had already removed. All three drivers match the main window by its title "keypaste" or a title ending " - keypaste". `approve-deny` also holds the disarmed half: a real click on the main window's rail takes focus with no second app, and past the arming delay Allow once must read not enabled, then enabled after a real click on the disarmed allow and its second, a click because macOS's accessibility focus moved no key window between the app's own windows (dev 42266266196, where it stayed disabled for 10 s), through a new `enabled` verb in each driver. A read right after a prompt opens would race the arming on a driver that takes a second to start, so it is not what the act asserts; `--selftest`'s `no-arming` and `never-armed` hold the verdict.
- **Titles** read "Items - keypaste", from the screen's fixed name alone, and "keypaste" on the unlock screen. A suffix rather than the prompts' "keypaste: …" keeps the main window apart from a prompt in the drivers.
- **A press on a button starts no move.** `PromptWindow` starts a move on a left press that nothing handled, and a disabled button is skipped by the press's hit test, so a press on a disarmed allow landed on the card behind it. It now asks the hit test with disabled controls included, and leaves any press on a button alone. The allows' enabling, Deny and activation are untouched, so a disarmed allow still answers nothing. Windows and macOS take the same check, where the one difference is that a press on a disarmed allow no longer starts their move.
- **The hand** stays on `Button.link` alone; `TermsLink` and Learn more are links. `Button.flat` and every switch, radio button, checkbox and segment lost it.
- **Toasts are centred, not top right.** Top right covered End, Done and other row actions, which `FourPlacesJourneyTests` and `OneHomeJourneyTests` found by a press landing on the toast.
