# 9.4 — Record supported vault workflows and compatibility

Completed 2026-09-23; the code was run at `0a6b05e` on branch `step-9.4`, source only. [PRODUCT](../PRODUCT.md) and [STEPS](../STEPS.md) own scope and the plan; this record is what the step did and is not revised afterwards.

## Scope as selected

**Build:** one gate that drives create, open, edit, organize, delete and recover, backup and restore, and change-access through the shipped CLI and the app on vaults KeePassXC made, including a keyfile vault, a keyfile-only vault, an AES-KDF vault and one carrying attachments, custom fields and custom data keypaste does not model. FEATURES then states the supported subset, what each workflow preserves and each refused variant, from that run alone. No full KeePassXC parity claim (D-0292).

**Verify (V-9.4):** each workflow's result opens in KeePassXC with its unmodelled data intact and each refused variant leaves the file byte-identical; a FEATURES claim with no step in the gate, or a fixture keypaste made, does not pass.

During planning the founder chose where the gate runs: the local `compat` profile, and a new KeePassXC job in `app.yml` on Ubuntu and Windows, because the gate drives the desktop and `ci.yml` deliberately builds no Avalonia.

## What changed for users

[FEATURES](../FEATURES.md#keepassxc-compatibility) now says which workflows work on a vault KeePassXC made, through the CLI and through the desktop. It says what KeePassXC still reads afterwards, what is refused without touching the file, and what was not exercised. The claim it replaces, that ordinary edits preserve attachments and custom strings, had no gate behind it.

Most of the table confirms behaviour already in source. One entry describes behaviour no document stated before. Restoring a history revision makes the entry that revision whole, as KeePass and KeePassXC do. If KeePassXC wrote the revision before it attached files or added custom fields, the restored entry no longer has them. The state the restore replaced becomes the newest revision, and restoring that revision brings everything back. The format boundary's own comment said the opposite; it now describes what the code does.

No product code changed behaviour.

## Evidence

**Preflight**, keepassxc-cli 2.7.10 on Windows 10, in a scratch directory:

- `import` of a KeePass XML document keeps:
  - meta, group and entry `CustomData`;
  - an unprotected and a protected custom string;
  - `Tags`;
  - an `AutoType` association;
  - a `History` revision.
- `import` works with `-p`, with `-p --set-key-file` and with `--set-key-file` alone. Given a path that does not exist, it writes an XML keyfile there.
- `import` and `db-create` both write KDBX 4.0 with AES-256 and `AES (1000000 rounds)`. `keepassxc-cli` has no KDF option.
- Two traps, both avoided in the gate:
  - A value marked `Protected="True"` in the XML crashes `import` (segmentation fault), because that attribute means inner-stream ciphertext. The gate marks such values `ProtectInMemory`.
  - On Windows, `attachment-export --stdout` alters binary bytes. The gate exports attachments to a file instead.

**The gate**, [verify-keepassxc-workflows.sh](../../scripts/verify-keepassxc-workflows.sh), drives [tests/Keypaste.AppDriver](../../tests/Keypaste.AppDriver/Program.cs), a new unshipped process. Each driver call opens a fresh app session and performs one act. It presses the command the screen binds to, on the view model the screen uses, through the unlock screen, the entry list and pane, history, Trash, the restore panel, export and access settings. A disabled command is a failure, so a greyed-out button cannot pass for a save.

KeePassXC imports one seed document three times: behind a password, behind a password and an XML keyfile, and behind the keyfile alone. It then attaches a 4 KiB random binary and a CRLF text file. On each vault the gate runs open, CLI edit, app edit, two history restores, organize, the delete-and-recover sequence, backup restore, export and the kind's access changes. Creation then runs once through each front end.

After every write, `intact` checks four things. KeePassXC opens the vault with its current factors and finds all seven markers outside `<History>`. Both attachments export byte-identical. The file reports the cipher and KDF KeePassXC chose, and is still KDBX 4. Every refusal compares the whole file and the backup count before and after. A driver refusal must exit 1, not 3.

The negative control runs first. A vault KeePassXC stripped of `note.txt`, and one imported without the entry `CustomData`, must each fail `intact`, and both did.

**Local run, keepassxc-cli 2.7.10, Windows 10:** passed. The negative control, then 27 steps across the three vaults and creation, with 31 refusals each byte-identical and taking no backup.

**Hosted runs**, `app.yml` dispatched on `step-9.4` at `0a6b05e`:

- Run 35891973017, on 4.6's own commit `4f1b3a9` with none of this step, passed the same job. This step changes no test and no view, only adding `InternalsVisibleTo` for the driver.

## Limits and follow-ups

The desktop was driven through its view models' commands, not through rendered windows or real clicks. 4.6 reads drawn frames, and F.2b3 covers native interaction. macOS was not run.

The gate did not exercise KDBX 3.1, ChaCha20 or Twofish, custom icons, or KeePassXC's browser-integration data. It also did not exercise an Argon2 vault made by KeePassXC, because `keepassxc-cli` cannot choose a KDF. The 32-byte, hex and hashed keyfile forms stay with [verify-keepassxc-keyfile.sh](../../scripts/verify-keepassxc-keyfile.sh), and recycling's rise to KDBX 4.1 stays with [verify-keepassxc-recyclebin.sh](../../scripts/verify-keepassxc-recyclebin.sh). The per-feature gates keep `Keypaste.VaultRestorer`.

The history finding is open as a product question for the founder. A restore that drops what was added after the revision is KeePass's behaviour, and it loses nothing, because the replaced state is the newest revision. But the desktop presents a restore as bringing back a revision's values. The question is whether keypaste should keep the current entry's attachments, custom fields and custom data when restoring. That would be a behaviour change with its own row and decision; this step records the present behaviour only.
