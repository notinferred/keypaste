# 4.6 — Verify secret drawing through the app

Completed 2026-09-23 on `87403cc`, source only. [PRODUCT](../PRODUCT.md) and [STEPS](../STEPS.md) own scope and the plan; this record is what the step did and is not revised afterwards.

## Scope as selected

**Build:** drive the secret-entry, reveal and recovery controls in a real visual tree and read what was drawn, rather than what a view model holds: the masked field, the held reveal on an env value, a history revision and the entry pane, each through its own interaction and each through a lock. Extend the existing automation-surface check to every control that draws a secret, so the window's accessibility surface while a value is shown equals the surface at rest.

**Verify (V-4.6):** a rendered frame holding a revealed value contains its characters and the same frame after the hold ends does not; a masked field's frame never does, at any length. The automation surface carries none of them in either state. Locking mid-reveal removes the value from the next frame. A view-model flag, a screenshot reader that never rendered, or an assertion about a property rather than a frame does not pass.

Selected by the instruction to build the next step, as the first ready code row in track order. No amendment.

## What changed for users

Nothing. The app's code is unchanged; this step changed how its tests see it. Before, every claim that a secret was or was not on screen read `RevealedValue.Rendered`, the string the control meant to draw, because the one headless test session drew no frames. The session now renders with Skia, and those claims are read from the frames it draws.

Two controls ever draw a secret: `MaskedInput`, in eleven fields, and `RevealedValue`, for the current password, a history revision and an env value. No screen draws a generated password, and Trash draws no field value.

## Evidence

Tests, all passing on Windows 10 Pro 19045 at the source above plus this step's changes. The session switch alone left the 410 existing app tests passing, in 22 s against 33 s before it; the suite is now 448 in 55 s.

- **The session.** [`HeadlessSession`](../../tests/Keypaste.App.Tests/HeadlessSession.cs) builds the app with `UseSkia()` and `UseHeadlessDrawing = false`. `Avalonia.Skia` was already in the test project's closure through `Avalonia.Desktop`, so no package was added. Pointer presses now reach controls by the platform's hit test.
- **The reader.** [`DrawnFrame`](../../tests/Keypaste.App.Tests/Rendering/DrawnFrame.cs) captures a frame, fails if there is none or it is one flat colour, and finds a text by drawing it alone in the drawing control's own typeface and size, cropping that to its ink and searching the frame by normalized cross-correlation. A drawn value scored 0.993 to 0.995. Dots in place of a value, a value where dots were drawn, and a same-length value sharing no character scored 0.336 to 0.475. The threshold is 0.9. [Its tests](../../tests/Keypaste.App.Tests/Rendering/DrawnFrameTests.cs), 3, show it finds a held value and then not, tells those two values apart, and that a click on the window reaches the drawn cell.
- **Reveals.** [`DrawnRevealTests`](../../tests/Keypaste.App.Tests/Rendering/DrawnRevealTests.cs), 6, run over the current password, a revision and an env value, in the app's `MainWindow` with the shell, `App.Bind` and the lock `App.ShowUnlock` performs. A mouse press at the cell's centre draws the value in the cell and not the dots, and no other secret in the vault is drawn. After release, the frame again holds the dots and no secret. While held, the window's automation surface equals the surface at rest, taken with the pointer over the cell, and carries none of the three secrets. That differential is new for the env value. Holding, then `Ctrl/Cmd+L`, leaves no secret anywhere in the next frame, and that frame draws the unlock screen's password placeholder.
- **Masked fields.** [`DrawnMaskTests`](../../tests/Keypaste.App.Tests/Rendering/DrawnMaskTests.cs) has 29 cases.
  - Each of the eleven fields is focused by a click and typed into through the window at lengths 1, 5, 24 and 64. The typed value is never found in the field, nor anywhere in the window from 5 characters. The mask is found in the field up to 24.
  - Each field then draws a value through its own template, which the search finds, so the search could have seen a leak.
  - The seven shell fields lock mid-entry, and the next frame holds neither value nor mask.
  - D-0099 over the whole window: two twelve-character values sharing no character leave the same surface on all eleven fields, and neither value is on it.

Mutations, each restored afterwards:

- `RevealedValue` keeps drawing the last value after release while `Rendered` says dots. The 3 reveal-and-release cases and the reader's own case fail. The 23 existing reveal tests, `RevealedValueTests`, `CurrentPasswordRevealAutomationTests` and `HistoryRevealAutomationTests`, all pass against it. This is the gap the step closes.
- `MaskedInput` draws what was typed. All 11 never-drawn cases fail at the one-character frame check, before any automation assertion. The 11 window differentials fail too.
- The session drawing with the headless stub again fails all 38 with "the session drew no frame".

## Decisions

## Limits and follow-ups

- The frames are Skia's in a headless window at scale 1, not a native compositor, a screen reader, another scaling or a real display. The native checks in [desktop.md](../desktop.md) remain the evidence for those.
- The reader looks for a value in the typeface of the control that would draw it. A value drawn elsewhere in a different typeface is not found by the frame search; it is caught only if it also reaches a text property the automation sweep reads.
- `Ctrl/Cmd+L` is delivered as a key event and the swap on lock is a copy of `App.ShowUnlock`, not the running app's (D-0306). `App.OnLocked` posts that swap, and `CaptureRenderedFrame` runs posted work before it renders. So "the next frame" here is the first after the lock's work completes, and a frame the platform draws between the lock and the swap is not observed. That frame could show only what was already on screen.
- Only the Windows run above is local. Linux runs this suite in `app.yml` on the next push, where `KpMono` resolves to a different font. The reference is drawn in whatever that resolves to.
- The desktop profile takes about 45 s longer, mostly whole-window automation sweeps and whole-frame searches.
