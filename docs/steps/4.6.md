## Limits and follow-ups

- The frames are Skia's in a headless window at scale 1, not a native compositor, a screen reader, another scaling or a real display. The native checks in [desktop.md](../desktop.md) remain the evidence for those.
- The reader looks for a value in the typeface of the control that would draw it. A value drawn elsewhere in a different typeface is not found by the frame search; it is caught only if it also reaches a text property the automation sweep reads.
- `Ctrl/Cmd+L` is delivered as a key event and the swap on lock is a copy of `App.ShowUnlock`, not the running app's (D-0306). `App.OnLocked` posts that swap, and `CaptureRenderedFrame` runs posted work before it renders. So "the next frame" here is the first after the lock's work completes, and a frame the platform draws between the lock and the swap is not observed. That frame could show only what was already on screen.
- Only the Windows run above is local. Linux runs this suite in `app.yml` on the next push, where `KpMono` resolves to a different font. The reference is drawn in whatever that resolves to.
- The desktop profile takes about 45 s longer, mostly whole-window automation sweeps and whole-frame searches.
