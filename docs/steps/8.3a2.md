# 8.3a2 — Fill a login on the person's answer or allowance

Completed 2026-11-16 on `t6-fill`, source only.

## Amendments

The founder's decisions of 2026-11-16:

- **Asked only on the person's click.** A page's own `get-logins` releases only what the person always fills on its exact origin, asks nobody and records only what it releases. A request the extension marks with `triggerUnlock`, which it sends for the field's key icon and the popup's Connect, may put the other matching items to the person. `keepass.js` now sends that flag with `get-logins` too, and the relay passes it on as `PersonAsked`; it decides whether to ask, never what is released (T-59).
- **Allowances on this computer, sealed.** "Always fill this item on" an origin is kept in `agents.toml` as `[[fill]]` sections under the agent rules' seal, not in the vault's `.keypaste/browsers` as the row said, so a synced or edited vault adds none (T-61). Sections are written only when there is one, so a file sealed before them still holds.
- **Per pairing.** An allowance names its pairing and when that pairing was made, so a later pairing of the same name inherits nothing, and applies only while the pairing exists.
- **`keypaste approve` fills** through a numbered list, a number filling that login and anything else denying, with no Always there.
- **Single-label hosts** such as `https://nas` match their exact host, scheme and port, asked every time with no Always; a name the Public Suffix List names, such as `com`, still gets nothing. This changes 8.3a1's refusal of `http://router/`.
- **Hosts written in Unicode** in an item's URL stay unmatched, by the decision's own condition: .NET's `IdnMapping` converts decomposed accents and a zero-width joiner differently in the app, which has ICU, and in `keypaste approve`, which runs invariant, so the two could disagree on which items a page gets. An item holds its host in `xn--` form.
- **The site's Daily driver sentence** is rewritten whole, its KeePassXC-Browser half, false since 8.1e, included.

## What changed

- **Core.** `SessionBrowsers.FillAsync` proves the pairing against the saved vault, reads the page's matching items through `Vault.ReadSavedBrowserItems` and `Browser/LoginCandidates.cs`, releases the allowed ones, asks about the rest through the gate with `Approval/FillPrompt.cs`, proves the pairing and reads the items again after the answer, reads each released login by UUID through `Vault.ReadSavedLogin` with its placeholders filled, checks the reply fits and the unlock is live, seals an Always, and writes every line at once before the reply through `RequestRecorder`. The browser line gains the fields `fill` and `unallow`. `KeePassInterop` reads KeePassXC 2.8.0's `BrowserHideEntry`, `BrowserOnlyHttpAuth` and `BrowserRestrictKey` on an item or up its groups as `BrowserService` resolves them, and the `Deny` hosts of `KeePassXC-Browser Settings`; its `Allow` hosts are not read. `AgentRules` and `AgentRulesFile` keep `BrowserAllowance`s; `IgnoredText` names them.
- **A browser's binding survives the relay attaching again.** The relay attaches before each of the extension's requests, and `SessionAuthority` dropped the pairing a check had bound with the old attachment, so through the real relay every fill was refused as unpaired; 8.1d's tests sent no fill through it. An attachment of the same build on the same connection, vault and unlock now keeps the pairing; another build, vault or unlock starts unbound.
- **The app** shows `Views/FillWindow.axaml`, the prompt windows' fixed layout with the logins by title, username and group, the origin with its site emphasised, the form's other site when there is one, and the Always box saying it lasts until removed; Deny is focused and Fill armed a second after a login is picked. Settings › Browser fill lists Always filled with Remove, and Activity names fill lines.
- **`keypaste approve`** lists the logins by number.
- **The extension** sends `triggerUnlock` with a forced `get-logins`, recorded in `extension/UPSTREAM.md`.
- **Tests** gain the fake browser's `get-logins=` and `click=`, the app driver's `fill <n> [always]` and `allowances`, and `Workspace.AddLogin`.

## Choices settled in the build

- A prompt lists at most nine logins, each one digit at the terminal; matching items past nine are not offered.
- A fill takes the one prompt slot and never waits its turn, so a click while any prompt is up gets no logins; a refusal or no answer holds that pairing and origin back a minute.
- A person's request records each matched item kept out, with its reason; a page's own load records none.
- The authority's own commit and frame-size checks stay after `FillAsync`, which makes both first; a lock in the instant between them can leave a line for logins never sent, as T-6 accepts.
- The waiting fill is not listed on Agents, as a pairing's confirmation is not.

What each shows:

- `SessionAuthorityBrowserTests`: attaching again as the same build keeps the proven pairing, and as another build does not.
- `RelayTests`: `triggerUnlock` reaches the owner as `PersonAsked`.

- `BrowserPairingTests`: the fill window's focus, arming, no password drawn, and Always listed in Settings and removed.

## Limits and follow-ups

- **Other tabs wait.** The relay answers one message at a time, so a browser's other requests wait behind a prompt (8.1c).
- **A second account on an always-filled site.** The extension keeps the logins a page's load got and does not ask again on a click, so a login not always filled there is reached with the popup's Connect, which does not run in Firefox (bug 1665380, `popups/popup.js`).
- **Always under a broken seal.** Ticking Always while `agents.toml` is ignored, or sealed by another vault, starts from the defaults and drops the agent rules too, as an agent's Always does (T-15).
- **Unicode hosts** stay unmatched (see Amendments).
- **No real browser** has filled a login: 8.3a3.
