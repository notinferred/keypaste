# 4.3b — Show actual requests, grants and audit outcomes

Completed 2026-09-23 on `main` above `bc33986`, source only. [PRODUCT](../PRODUCT.md) and [STEPS](../STEPS.md) own scope and the plan; this record is what the step did and is not revised afterwards.

## Scope as selected

**Build:** Agent Activity shows the requests waiting at the app's session and the grants in force, with their client, entry, field and remaining lifetime, read from the session authority. It shows audit history read from the records `keypaste-mcp` wrote. A Revoke action ends one grant, or all of them, in the authority, so the next matching request is decided again. The view says when the authority or the log cannot be read instead of showing that as no activity. Traces to PRODUCT §§1 and 3.3.

**Verify (V-4.3b):** with a real `keypaste-mcp` request waiting at the unlocked app, Agent Activity lists it. After Approve it lists the grant, and the history shows the prompted grant from the audit file. Revoke makes the same request ask again, and a lock empties both lists because the authority holds nothing. A missing or unreadable audit log is shown as unavailable. A list built from the view model's own events, or history read from anything but the log file, does not pass.

The founder approved the plan with one choice made while planning: the history shows only the audit records that name the app's current session, with the filter and its counts stated and the Log screen left for the whole file (D-0331).

## What changed for users

- **Waiting and granted.** Agent Activity lists the request in front of the person in the prompt window, and every grant in force. Each row shows the client's name, its label ("none configured" without one), the entry, the field and the seconds left: until the gate answers for the person, or until the grant ends. The screen reads again every second, so both count down. Nothing on the screen carries a value. The rows are read from the session authority that answers agents, so they say what the next request will meet (D-0330).
- **Revoke.** Each grant has Revoke, and the list has Revoke all. A revoked grant is zeroed at once, and the next request it would have answered opens the prompt again. A revoke starts no refusal cooldown and writes no audit line.
- **This session's history.** Below the lists are the audit records naming the app's current session, rendered as `keypaste log` renders them, under a heading such as "3 records of 12 in …/audit.jsonl, session …". Rows the chain does not vouch for are marked, and an edited log is said to be edited, as on the Log screen. The history is re-read when the file's length or write time changes. A new unlock starts with an empty history, because it is a new session.
- **Unavailable is not empty.** While the app is locked or not answering agents, the screen says that waiting requests and grants cannot be read. A missing log reads "History unavailable: there is no audit log at <path>". A log that cannot be read or checked says so with the reason. None of these shows as a session in which nothing happened. The Log screen still treats an absent log as a machine nothing has asked yet.
- **Log screen.** It now reads, checks and renders through the same helper as Agent Activity, with its wording unchanged. A directory at the log's path used to read as "Nothing has asked… yet". It now reads as a log that could not be read.
- The placeholder saying the app did not answer agents yet is gone.

6. A request waiting at a lock is listed before it. After the lock the screen says requests and grants cannot be read. After a new unlock, nothing is listed and the new session's history has 0 records.
7. With the log replaced by a directory, the history is unavailable ("Access to the path … is denied" on Windows).

## Limits and follow-ups

A grant approved just before Revoke all can be stored just after it: the handler stores a grant once the person's answer returns. It then appears in the list at the next tick and can be revoked there.

A revoke writes no audit line, because the approver writes none (D-0084), so the history cannot show that a grant was ended early.

History reads the log at `KEYPASTE_HOME` or `~/.keypaste`. A bridge started with `--audit-log` writes somewhere the app does not look, and its records never appear here. A session's history is its records alone, so records a bridge wrote before attaching, or with no session, are only on the Log screen.

`keypaste agent` has the same `Activity` and revoke on its authority but no command to use them.
