# 4.4 — Approve and deny in the desktop

Completed 2026-09-23 on `main` above `3d56180`, source only. [PRODUCT](../PRODUCT.md) and [STEPS](../STEPS.md) own scope and the plan; this record is what the step did and is not revised afterwards.

## Scope as selected

**Verify (V-4.4):** a real `keypaste-mcp` request against the unlocked app raises the prompt; Approve returns the field, and the audit line records a prompted grant naming the session. Deny, the timeout, closing the prompt, the client disconnecting and a lock each return a denial with the matching method and withdraw the prompt. An agent reason written to imitate controls cannot change the prompt's layout or buttons, and the prompt's automation surface never carries a released value. A prompt driven only through its view model, or a denial observed only in the view, does not pass.

The founder approved the plan with two choices made while planning:

- **Approve is armed after one second.** The prompt is a window of its own and can appear under a pointer about to click something else. Approve is disabled until the prompt has been on screen for a second; Deny, Escape and closing work at once (D-0326).
- **The app consults no policy file.** `keypaste agent` releases what a rule in `policy.toml` covers without asking. The app keeps `PolicyGate.None`, so every release from it follows a press of Approve. Honouring policy in the app is left as a gap.

Two things were missing and are part of this step. The approver listener did not notice a bridge hanging up while its request waited, so the prompt stayed up for the rest of its window (D-0327). And `ApprovalPrompt` carried no client label, which the prompt must show.

## Evidence

**Tests:**

- `DesktopApprovalTests`, 12, new. Each composes `AppAuthority` with the shipped `WindowApprovalChannel` on a manual clock, reaches it over the app's real endpoint with `ApproverClient`, and draws the prompt with Skia on the headless platform, clicking through its hit-testing.
  - Approve returns the field as `Granted` / `Prompt` in the session, after the prompt showed the label, entry, field and "60 seconds". The window comes down, and the automation sweep D-0099 uses finds no sentinel in it.
  - Deny, Escape, closing the window, 45 seconds on the clock and a lock each return a denial as `Prompt`, `Prompt`, `Prompt`, `TimedOut` and `VaultLocked`, with no value, and the window comes down.
  - A bridge that cancels its exchange and hangs up takes the window down.
  - A request withdrawn before its window is drawn is refused and never drawn.
  - Clicks on Approve before one second has passed answer nothing, and one after it approves.
  - Focus starts on Deny, and Enter there refuses.
  - A second request from another connection while the prompt is up is `Busy`, with one window.
  - A 400-character reason of fake buttons, a fake verdict, line breaks and a bidi override draws the same two buttons, neither a default, with the same bounds in a window of the same size as an ordinary reason does, and its text is one plain `TextBlock` holding the sanitized reason.
- `ApproverListenerTests`, 2 new, over a real pipe. A peer that gives up its exchange and hangs up, as the bridge does when its client cancels, has its request withdrawn and is disconnected. A peer that sends mid-exchange has its request withdrawn and its connection ended with no reply.
- `ApprovalPromptTests`, 1 new and 1 extended: the label is sanitized and capped like the client's name and absent when none was given; the member list now includes `Label`.
- `ApproverHandlerTests`, 1 new: the prompt carries the bridge's label.
- Tests about serving the vault rather than asking now pass `NobodyToAsk`, a test channel with nobody behind it, since the channel is required.

**Gate**, [verify-desktop-approval.sh](../../scripts/verify-desktop-approval.sh), new: the shipped Release `keypaste` and `keypaste-mcp` against `Keypaste.AppDriver hold`, which now composes the app's own prompt window, as launch does, on a headless Skia display. It prints what the drawn window shows and when it comes down, and answers `approve`, `deny` and `close` by hit-tested clicks or closing the window. Each case uses a new bridge labelled `ci-probe`:

1. The prompt shows `label=ci-probe entry=env/ci/DEPLOY_KEY field=password for=60 seconds`. Approve returns the credential, audited as `granted` / `prompt` in the app's session under the label; the credential reaches neither the audit log nor the driver's output.
2. Deny and closing each return a `prompt` denial in that session, and the prompt comes down.
3. An MCP `notifications/cancelled` for the waiting request takes the prompt down and is audited as `cancelled`. This was the planned preflight: the MCP SDK does cancel the tool call, so the gate keeps the case.
4. A bridge killed with its request waiting takes the prompt down. Closing the bridge's standard input does not, because the MCP host waits for the call in flight before it exits, so the gate kills it.
5. A lock returns a `vault-locked` denial in that session.
6. After a new unlock, nobody answering returns a `timed-out` denial in the new session.

It passed on Windows 10 in 52 s. [verify-session-authority.sh](../../scripts/verify-session-authority.sh) now denies its request in the prompt and checks a `prompt` denial in the session. ## Limits and follow-ups

The app reads no `policy.toml`, so a rule that releases silently at `keypaste agent` prompts in the app. Whether the app should honour policy is not in any STEPS row; FEATURES records the gap.

No gate launches the real Avalonia process. The driver composes the same channel and window on a headless display, so the prompt's appearance over other windows, `Topmost` and focus on a real window manager are not observed; that belongs with F.2b3's window-manager clicks, and a person's rendered layout review is outstanding.

Closing a `keypaste-mcp`'s standard input does not end a call it has in flight: the bridge waits for the answer, so its prompt stays until it is answered or times out. A client that goes away without cancelling or killing the bridge leaves its prompt up for the rest of the window.

Agent Activity still lists no waiting request, grant or audit line; that is 4.3b. Connecting a client from the app is 2.6a.

`keypaste agent`'s terminal does not show the client label. The terminal channel was left alone, because the demo transcripts `verify-demo.sh` checks print its prompt.
