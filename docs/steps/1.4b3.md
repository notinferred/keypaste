## Amendments

- D-0542 also lists a request that finds the file changed among the merge's triggers; the row names the watch, the poll and a refused save, and only those are built. A request in that window is refused as `vault-changed` and starts no merge, and the watch or the poll merges within five seconds (D-0638); 1.4b4 moves detection into Core for both owners.
- G4 merges the open copy with KeePassXC, and an open copy exists only in memory, so the app driver writes it through a seam made for that, `Vault.WriteCopyTo`, and gives it unsaved changes through core, the state a refused save leaves (D-0641).
- Two G cases depend on what 1.4a left unmeasured, whether KeePassXC keeps a version keypaste read intact: G3 measures it across KeePassXC's own save, and G4's change stamped before the base across KeePassXC's export and import. Each prints what it measured and asserts the rule that then applies, lineage or time (D-0538).
- Integration with 8.1d found that a connection's write whose merge met another key locked on the connection's own thread, and the lock waits for every connection to end (D-0392), so it waited on itself and the window froze. `WriteFor` now has that lock run on a thread of its own, as a lock asked over the pipe already does, and answers the write first. The same integration aligned a pairing check refused for another program's save with D-0640's words.
- The merge gate's G6 found that KeePassXC's recycle stamps an item without keeping a version, so keypaste's merge kept the person's untouched copy in history and the notice said both had changed it. By the founder's decision such an item, differing from the open copy only in place and stamps, is now the file's whole (D-0674); `VaultMergeTests` holds it, and a later save from a copy forked before the app's saved change, which a first form of the rule lost, still keeps that change in history.

## What changed

- **The session** (D-0638). `AppVaultSession` merges another program's save only through the owner serving the unlock, which `SessionHost` installs per unlock as `SessionAuthority.Merge`, so the withdrawal, the save and the audit line are the owner's (D-0622). One edit gate holds every write, reload, access change and merge; a save refused as changed on disk merges at once and is answered as saved when the merged copy holds the edit, and a write that took itself back is answered as merged without it (`WriteResult.Merged`). A refusal is kept with the digest of the bytes it refused, so the watch and the poll leave those bytes alone; a key that no longer opens the file locks with `ReloadRefused` once the gate is released, as a reload's and an access change's locks now are. A merge asked again for one save finds nothing to do and withdraws nothing.
- **The shell** (D-0639). `ShellViewModel` merges on the folder watch's settle and the five-second poll on a thread of its own, the title bar saying `· merging`, then `· updated <time>` for a merge that took nothing; a merge that carried the open copy's changes sets the notice from `MergeNotice`, which names the edits it saved, the items changed in both, those kept against a deletion and the groups renamed in both, by name and never by value, and stays until dismissed. A refused merge shows the danger notice with its reason and Reload, now offered only then. An item open for editing is left as typed and the Items list reloads under it. History reads a merge's line as keypaste app's "Merged another program's save".
- **What agents are told** (D-0640). `ToolText.VaultChanged` says the desktop merges by itself and to try again in a moment, then to ask the person to read the notice or restart `keypaste approve`; the owner's recorded reason says nothing is released until keypaste merges that save or a person reloads.
- **The gate.** `scripts/verify-keepassxc-merge.sh`, new, sourcing `lib/common.sh` and `lib/kpxc.sh`, runs G1 to G8, G11 and G12 against vaults KeePassXC imports, with the app held by `Keypaste.AppDriver hold`, which gains `merge`, `status`, `restore`, an `edit` with its own password, the `unsaved-` lines and `write-open`, and prints a `merged` line, in the notice's words, for every merge. It reads KeePassXC's exports with a small Node reader it writes beside its vaults. It runs in ci's compat jobs on the three runners and in `verify.sh compat`, and shellcheck reads it in the workflows profile.
- **The current-state gate.** `verify-current-state.sh` step 5 now has the app's refused edit merged with another program's save and the next request served in the same session and asked again, and keeps Reload for a file holding another vault.
- **Records.** THREATS' opening, T-15, T-29 and T-32, SECURITY's editing section, the desktop, replace-dotenv, mcp-setup and policy guides and FEATURES say the desktop merges; mcp-setup and policy list `merged`.

## Limits and follow-ups

- **The merge gate has not run.** `verify-keepassxc-merge.sh` runs only in the batch's full run, in ci's compat jobs, as do `verify-current-state.sh`, in app's desktop gates, and shellcheck, in ci's workflows job. The compat job's limit went from 18 to 38 minutes and the gate's step has 20, with no measured run; the batch run's times set them to about twice the slowest green.
- **Whether KeePassXC keeps a version intact is still to be read** from the batch run's G3 and G4 lines. If it does not, a merge cannot show lineage for an item KeePassXC saved without changing it, and the cases expecting a save taken as it is fail with the measurement printed above them.
- An edit made while a merge waits for a hardware key's touch holds the window until the key answers or times out, since the window's thread waits on the edit gate, so neither the title bar nor the touch prompt paints meanwhile.
- A merge refused because the hardware key did not answer is tried again at the next save or the file's next change; the notice has no button for it.
- Screens other than Items and Env Sets are built again after a merge, as after a reload, so what was typed in a form there, Settings' master password change say, is lost.
- `keypaste approve` merges nothing before 1.4b4, and its refusals still say to restart it.
