## Amendments

The founder's selection added what follows, each applied: sorted state is presentation only, a sort keeps the selection and pane as Q.18 left them, comparison lives in one place, Last used sorts by real times with never last, the log's chain is untouched, heads are controls, and resizing has a keyboard equivalent, a minimum and a target clear of the sort press. ## What it does

A head is a `ColumnHead`: a button 20 tall, its column in capitals, with an arrow beside it while the rows run by it, in the text's colour, and an accessible name such as "Title, sorted ascending". The first press sorts, ascending for text and newest first for a time, and the next reverses. The edge after a head is a `ColumnGrip`, 20 by 20, lying over the head's end so a press on it never sorts; it moves by a drag, or by 8 with the left and right arrow keys while in focus, named "Resize the Title column". `TableColumns` is the grid a head row and every row share. `TableState` holds one table's order and widths, `TableStates` the three tables, in the shell, so they outlive the screens, and `TableSorting` is the one place text is compared.

## Decisions

- **Default order.** Items stay in the vault's order, with no arrow, as they were. Trash stays latest deleted first and the log newest first, each drawn as an arrow on its time column, since those orders are that column's. The log's own order stays the file's, the only one the chain vouches for, so a record whose clock stepped back or forward, or that has no time, keeps its place. Pressing Time sorts by the records' times, undated last, with the file's order breaking a tie.
- **Two states, not three.** A third press does not go back to the default, as a native table's would not and as "again to reverse" says. The way back is View › Reset table order and widths, on only while the table in view differs, since a person could otherwise never regain the vault's order or the log's file order: two presses on the log's Time give newest first by the records' times, and that is kept as a choice.
- **Persistence.** Both persist, in `[[window]]`, as two keys, `table_sorts` and `table_widths`, written only for a table that differs from its own way, so a window nobody touched writes neither and the file's hash holds. That makes seven of the section's eight keys. Text holding anything but lowercase letters, digits and the separators reads as the table's own way, as does a column it does not have.
- **Widths are shares once a table is resized.** Its pixel columns become shares of the room too, each column keeping its least, so a table can never push a column off screen, at any window width, and needs no sideways scroll on Items or Trash. Until the first resize each column keeps its own width, so the tables look as they did.
- **An edge moves the two columns beside it**, not the whole table: a column narrower and the next wider. The last column has no edge of its own; the edge before it sizes it. A narrow window's dropped column is skipped, and comes back in proportion.
- **A sort by a dropped column gives way.** With Username, URL or Where gone under 840, the table takes its own order while it is gone, with no arrow, and goes back to the chosen one when it returns. No row runs in an order the screen cannot show.
- **A held row stays at the top.** `_pinned` is inserted after the sort, so an item an edit renamed out of a search stays where the person is looking, out of order, until the next question. Reselect, the selection and the pane go through unchanged, since a sort calls none of them; a Trash sort takes its selection back and keeps an armed Delete for good armed.
- **Blanks last.** An empty username or URL, an item at the top level under Group, a log cell reading "—" and a time not held sort last in both directions, as never answered does. In use sorts as the latest there is.
- **Ties.** Items by title, then group, then ordinally; Trash by latest deleted, then ordinal title; the log newest first by file position, reversed under oldest first, so a sorted log's days keep together.
- **The log's day dividers stay on, under any sort.** A divider appears wherever the day changes, so every row's clock still sits under its own date. A sort that interleaves days repeats dividers, which is noisy but true; the frames show "Today, Yesterday, Today" under Actor.
- **Sorted activity reorders live.** Sorted by Last used, a new picture rebuilds the list only when the order changed. `ApplyActivity` also updates the rows of a search result, which had kept the words of when the query was made.
- **No menu commands for sorting or sizing.** DESIGN's rule 1 says every command is in the menus. A head and an edge are direct manipulation of what they sit on, as the pane's divider is; only Reset, which has no place on the table, is a command. The founder may want View › Sort by.
- **Grips are tab stops**, five each on Items and the log and two on Trash, which lengthens the way through the head row. A key on the head alone would be shorter but neither discoverable nor named to a screen reader. A grip's tooltip gives its name and its keys, and its automation peer is a slider whose value is the column's drawn width, with its name and help, which a screen reader can change and is told of when it changes. Its line is the control edge at rest and changes as one does under the pointer.
- **Least widths**: Items 64, 64, 56, 56, 56, 88; Trash 96, 96, 124, its time needing that; the log 64, 56, 56, 64, 56, 64. These are each column's drawn width. A sorted head's arrow keeps clear of the edge lying over its head's end, however narrow the column, so pressing it sorts; the text gives way first, trimming with an ellipsis, and its tooltip gives its name. An unsorted head keeps no room for an arrow. This was preferred to raising each least to fit its whole text and arrow, which would take Username to 108 and cost URL its 72 at the 840-wide window.
- **`LogViewModel` became disposable** to leave the table's event, the same as the other two; the shell already disposes content on every navigation.
- **Trash's rows and its title cell became a grid**, since a horizontal `StackPanel` gave the title no limit and a narrowed column let it run over the next.

## Limits and follow-ups

A head's focus ring was clipped to the head and drew nothing, which a frame showed and no test had; `ClipToBounds` is off on heads, and a test holds it. The same clip shows on New, so BACKLOG holds whether ordinary buttons show a ring.

**Sorting is not culture-aware until Q.16.** `InvariantGlobalization` is set for the whole repository in `Directory.Build.props`, so `CurrentCulture` is invariant, and a probe under it showed `CompareInfo` ordering "é" after "z", `Normalize` a no-op and `NumericOrdering` ignored, so "item 10" sorts before "item 2". Case is ignored, ties are deterministic, and `TableSorting.CompareText` already asks the current culture, so lifting the setting brings accents and a language's order with no change there. "item 2" before "item 10" takes `CompareOptions.NumericOrdering` as well, which the code does not ask for yet because nothing here could show it working. Lifting it reaches every string operation in the app and needs ICU on Linux, which is packaging, so it was left to the row that owns cultures. Nothing was hand-written in its place. This is the one requirement of the selection not met.

No live region says a sort happened: a head's name changes in place with focus still on it, and whether a screen reader reads that out has not been heard. A drag's cursor and a real pointer have only run headless. Right-to-left is Q.16's, and a grip moves as drawn, left to right.

Sorted by Where or Secrets, the log compares what the cell draws, which can be a recipient for a share link.
