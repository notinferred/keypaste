# C.1b — Resolve projects from tagged fields

## Amendments

The row as selected is in Git at `a432ade`. The task was built by an agent from the orchestrated 0.5.0 plan without further founder direction. Each choice below fills what the row left open; the one addition to its refusals is marked.

- An entry is a legacy variable when it sits in the environment's `env/` group and none of its own tags puts it in any project; an ordinary or malformed `env:` tag leaves it a variable. An entry in `env/<project>` tagged into a project gives that environment its fields, never its title, which is where C.1c's `env/<project>/.env` home entry lives.
- A variable field is a custom field `EnvConvention.IsEnvNamedField` accepts. Added to the row's refusals: one named like a standard field in another case, such as a `PASSWORD` KeePassXC wrote, joins the set and refuses it, naming its entry. The row's name rule admits it, while C.5a's row says no such custom field ever leaves and D-0369 says keypaste never writes one, so it is neither released nor silently left out; `env tag` names it among the joining fields by the same rule.
- A placeholder is one of KeePassXC's, matched by name in any case: `{TITLE}`, `{USERNAME}`, `{PASSWORD}`, `{NOTES}`, `{URL}`, `{UUID}`, `{TOTP}`, `{DB_DIR}`, `{DT_…}`, and `{S:…}`, `{REF:…}`, `{URL:…}`, `{T-CONV:…}`, `{T-REPLACE-RX:…}` (`KeePassPlaceholders`). Other braces, such as a JSON value, pass. A refusal names the placeholder's keyword, never the value around it.
- Each refusal ends with the entries it concerns in parentheses, in ordinal order, and the heading names `'<project>/<environment>'` instead of the `env/` group. An expired tagged entry refuses each key it gives; one with no variable fields gives nothing and refuses nothing.
- Protection follows every source entry: a set is asked live with Allow once only when its environment is protected or any source entry's path or own tag names a protected environment (D-0371); a timed grant already stored for its names is not used; a scoped token needs `allow-prod` and a live answer for such a set, and a bundle refuses it, because D-0348 covers every release.
- `env ls <project>` takes a legacy project's environments from its groups and tags together, so `-p` and `--profiles` reach a tag-only environment; its legacy variables are the group's untagged entries, and each tagged entry's variables follow beneath it. `--json` adds `keys` per member and `entries` per key. `env export` refuses a key two entries hold, naming them, and `--dotenv` exports tagged values too, refusing a custom field named like a standard one, which a listing shows but no path releases (D-0388). `env diff` without a pair compares the first environment with each other, since a tag-only project may have no `dev`.
- The desktop's Env profiles takes its columns and cells from `EnvMatrix`, each cell's tip naming its source entries, and its `.env.keypaste` preview and export from the listing `env export` uses, refusing a key two entries hold. A tagged key has no value row to copy, replace or remove until C.1c writes it, and tag-only projects reach the app with C.4.
- `run --session` writes no audit line today; its releases are recorded in the owner's ledger by source entry, and the audit lines that exist, the bridge's `run` and scoped tokens, name source entries.

## Limits and follow-ups

- Keys are written onto tagged entries only with `keypaste set --field` until C.1c; the desktop cannot copy or edit a tagged key yet.
- Placeholders are refused, not resolved, until P.3b1.
- The bridge's default exposure is `env/**`, so an agent's `run` of a set with a tagged entry outside it is refused as out of scope until C.5b adds tag selectors.
- The projects gate now drives the app, but a change to the app alone does not select the compat lane, so a pull request or dev run for such a change leaves that half to the full runs on `main`.
- The prompts still say "profile" for an environment; N.6 owns the wording.
- Found on the way and not caused by this step: the four macOS `EnvLaunchThroughAppTests` (F.28) and the broad Windows dev job's 30-minute limit (F.39), both since repaired, and the Windows `SaveTimingTests` failure (F.34), still open.
