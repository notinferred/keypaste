# 8.3a3 — Prove fill in real browsers

Completed 2026-11-16 on `t6-fill-browsers`, source only.

## Amendments

The founder's decisions of 2026-11-16:

- **Store installs wait for 8.1g.** The hand check of the extension installed from the stores, and the Chromium copy carrying the Web Store item's key, move to 8.1g's acceptance; this step proves the test build, the same code under the test IDs.
- **Every browser on every platform.** Chrome, Edge and Firefox on Windows, macOS and Linux, and Brave, the fifth browser keypaste writes for. Windows and Linux are checked on GitHub's runners in their own branded browsers by `verify-browser-fill.sh --branded` through `dev.yml`, never a gate, since a runner image changes its browsers; macOS also on the founder's Mac, where the founder paired and filled in the real app.
- **One job.** The gate runs in app's `extension` job after the pairing gate, not in a job of its own. Geckodriver and Firefox ESR are pinned by digest, as in `verify-extension-load.sh`, Edge and Brave by version and digest, Chromium by Playwright's lockfile.
- **Edge joins the CI gate**, under the Edge test key, so it is named as the Edge Add-ons build.
- **A second account on an always-filled site.** A click on the key icon asks keypaste again when the page's logins came only from its load (8.3a2's limit).
- **The defects the browsers showed are fixed here:** the extension's dropped first message and its logins served across origins, and Brave's manifest on macOS.
- **Pairing's four acts** were found overdone; a one-step pairing is a BACKLOG entry.

## What changed

- **The gate.** `scripts/verify-browser-fill.sh` and `extension/tests/fill-in-browsers.js`, sharing the driver, pairing and geckodriver code with the pairing gate in `extension/tests/browsers.js`. A Node HTTPS server with a certificate made for the run serves test names that Chromium-family browsers map with `--host-resolver-rules` and trust by its key's SPKI, and Firefox resolves with `network.dns.forceResolve` and takes with `acceptInsecureCerts`. Each browser runs alone, in a profile folder of its own whose `NativeMessagingHosts` is the folder keypaste wrote, since a browser refuses DevTools on its default folder; the extension is loaded over the DevTools pipe, as branded Chrome no longer loads one from its command line, and the browser's own password manager is off. The app driver's fill prompt line names the form's other site.
- **The extension's worker** adds its message listener in its first turn and waits for its start inside it; upstream added it after reading storage, so a Connect, or any page's message, that started or reached a starting worker was dropped. Windows dropped the first Connect in three browsers of four every run before this, none after.
- **A tab's logins** are reused only on the origin keypaste released them for; upstream reused them on any page of the tab until the browser reported its new address, so a page of another site that asked first got the last site's logins, and a refused prompt on a subdomain filled the login allowed on its parent.
- **Brave on macOS** reads Chrome's manifest folder, not its own: with Chrome's file absent it reported no host while keypaste's file was in Brave's and in Chromium's folders. `HostPlaces.Slot` gives Brave Chrome's manifest on macOS as on Windows, so they turn on and off together and Settings says so; on Linux Brave reads its own.
- **Documents.** SECURITY's Browser fill subsection and its Audit limit; T-48 and T-58's tests; T-58's origin rule for a tab's logins; FEATURES; `extension/UPSTREAM.md`.

## Evidence

- `verify-browser-fill.sh --branded` through `dev.yml` on `windows-2025`, `macos-15` and `ubuntu-24.04`, every browser alone: Chrome 156 and 157, Edge 156 and 157, Brave 1.99.57 and Firefox 160. In each, a click fills the item's site after the prompt, Always fills it on reload unasked, the click on an always-filled page still offers the other login and keypaste records its release, a refused subdomain fills nothing, a lookalike and another tenant of `github.io` get nothing and nobody is asked, an `http` page and a form posting to another site are asked with no Always and the latter named, a cross-origin frame is refused by the extension before keypaste is asked, no keypaste outlives its browser, and the log names origins only, never a path, query or password.
- On the founder's Mac (macOS 26.6), the app's internal build held a test vault; Chrome 157.0.8103.79, Edge 157.0.4341.60, Brave 1.99.57 and Firefox 160.0 each paired through the person's confirmation, filled on the person's Fill and offered nothing on a lookalike.
- `BrowserHostsTests`, `BrowserVerbTests` and `BrowserHostSettingsTests` on this Mac; `BrowserHostTests` in CI.

## Limits and follow-ups

- **Store builds** are 8.1g's.
- **Brave's first click** on a page just opened after a fill elsewhere on the site did nothing twice in about ten Linux runs, and once in Chrome on macOS; the gate allows one more click and prints it (BACKLOG).
- **Edge on Windows** closed the extension's list when a username was typed into it, so Enter submitted the form (BACKLOG); the gate proves the second login by its release and the list, not by picking from it.
- **Brave's folder on macOS** was seen with a profile folder of the gate's own; its default profile was not driven.
- **A login released on an origin** is reused by the extension for that origin until the tab leaves it, without a new line in the log (T-60).
