# Release contract

[ROADMAP](../ROADMAP.md) owns what each release is planned to contain and [STEPS](STEPS.md) its tasks; [CHANGELOG](../CHANGELOG.md) records changes by version. A release requires evidence that users can download, install and exercise its advertised behavior.

## Status vocabulary

| State | Required evidence |
|---|---|
| Implemented | Source and relevant behavior checks pass. |
| Packaged | A versioned distributable exists, its contents are checked and its checksum is recorded. |
| Published | That distributable is available at a permanent, anonymous public URL. |
| Installation-verified | The public download is verified, installed and exercised on the claimed OS and CPU architecture, with retained results. |

A desktop release is complete when every target it advertises is published and installation-verified. The first desktop release is 1.0.0: it covers Windows x64, macOS arm64 and Linux x64 and ships together with the next CLI/MCP version, which takes the same number; existing CLI/MCP downloads retain their four targets. Record the tag, source commit and artifact hashes. Expiring CI artifacts do not establish publication.

## Floor evidence

[release-targets.json](../release-targets.json) records OS floors using the evidence types below. [verify-release-matrix.sh](../scripts/verify-release-matrix.sh) checks this vocabulary and the requirements for each value.

| `floor_evidence` | Meaning | Gate requirement |
|---|---|---|
| `container-check` | A repository check runs the binary in a named compatibility image | An `os_floor`. Currently `linux-x64`: Debian 12 must run it and Alpine must refuse it. |
| `runner-image` | The floor follows from the build image | An `os_floor`. NativeAOT and the self-contained app link against the build machine's glibc. |
| `unverified` | The asserted floor has no supporting run | An `os_floor` and a `floor_caveat` reproduced on every page stating the floor. |
| `cited` | An external source states the floor | An `os_floor`, `floor_citation` and `floor_caveat`; this does not establish an observed installation. |
| `none` | No floor is claimed | No `os_floor`. |

`macOS 14` and `Windows 10 1809` are cited .NET 10 floors. Keypaste has no recorded installation on those minimum versions. The Linux x64 check establishes Debian 12 compatibility; success there alone does not prove the stated glibc 2.35 minimum. The CLI/MCP installations recorded under [Published releases](#published-releases) ran on runner images above these floors, as 4.7b and 4.7e1's internal desktop candidates did.

## What exists

[release.yml](../.github/workflows/release.yml) builds CLI/MCP natively on four targets. Tags must match the source version, name a commit on `main` whose required gates passed in a full run (a dispatch, the weekly schedule or the tag's own run; ci's with its real-tools jobs, which a dispatch runs with `-f tools=true`), have a changelog section, and carry a vendored Public Suffix List at most 60 days old, which [update-public-suffix.sh](../scripts/update-public-suffix.sh) refreshes as an ordinary commit before each release. The workflow tests the actual NativeAOT binaries, including KeePassXC compatibility, before packaging. Linux x64 is checked on Debian 12 with an Alpine rejection control; ARM64 has no equivalent container check. Each package job fails unless the archive's `THIRD_PARTY_NOTICES.md` lists exactly the NuGet packages that product ships, so a dependency change regenerates its section with [third-party-notices.sh](../scripts/third-party-notices.sh) `generate` after a restore of both solutions.

Publication rechecks transported hashes, includes source and licences, writes a release manifest and attestation bundle per published component into one version prefix, checks each attestation, and restricts files and counts before uploading through [publish-release.sh](../scripts/publish-release.sh). The desktop packages are not rebuilt there: `release.yml` resolves the tag's `app.yml` run through [require-green-gates.sh](../scripts/require-green-gates.sh) `--run-id`, downloads its artifacts and holds each to [verify-desktop-candidate.sh](../scripts/verify-desktop-candidate.sh) before staging it, then attests what it publishes. The manifest and Sigstore bundle are published with the release, so provenance survives artifact expiry; [verify-provenance.sh](../scripts/verify-provenance.sh) checks the public bytes after upload and on `install.yml`'s Linux leg. `publish-release.sh` is the sole bucket writer. It requires a successful, parseable listing naming the requested empty prefix and a positive-control listing of an existing release. Both key counts must be numeric. Invalid, unavailable or denied responses refuse publication. [verify-release-destination.sh](../scripts/verify-release-destination.sh) exercises these cases without credentials in CI and the release guard. Manual dispatch builds and verifies without publishing. Downloads are served from R2; GitHub Releases are not the distribution channel.

The desktop uses the operating system's ICU and bundles none. On a Linux machine with no libicu, `IcuFallback` turns on invariant globalization before anything reads a culture, since .NET would otherwise end the process, so the app starts with ISO dates and code point sorting; [verify-no-icu.sh](../scripts/verify-no-icu.sh) holds that against the published `linux-x64` payload in a container with no libicu, by `--selftest`, which reports how a date reads and how text sorts, and by finding the app's window under Xvfb; the built AppImage is held to the same selftest. The `keypaste` binary stays invariant.

[app.yml](../.github/workflows/app.yml) packages three desktop targets, checks versions, runs a vault selftest, attests archives built from a tag and retains them for seven days. On `win-x64` it also wraps the staged payload in the per-user MSI that [release-targets.json](../release-targets.json) declares, named and labelled internal and unsigned. [verify-windows-installer.sh](../scripts/verify-windows-installer.sh) checks its name, version, publisher, scope and missing signature, then extracts it with `msiexec /a` without installing, and requires byte-identical payload files that pass `--selftest`. Every desktop payload carries the NativeAOT `keypaste` that [publish-desktop-bridge.sh](../scripts/publish-desktop-bridge.sh) adds beside the app, so a client connected from the app has a bridge to start as `keypaste mcp`; the MSI check requires `keypaste mcp --help` to answer, and so that a terminal runs it as `keypaste` the checks also require the MSI's one `Environment` row appending its folder to the per-user PATH, the AppImage's `AppRun cli` to start it, and on `osx-arm64` [verify-macos-cli-link.sh](../scripts/verify-macos-cli-link.sh) to find the built bundle's copy from a new login shell through a link at `/usr/local/bin/keypaste`. On `linux-x64` [build-linux-appimage.sh](../scripts/build-linux-appimage.sh) wraps the same payload in the declared internal, unsigned AppImage with appimagetool and a type2 runtime, both pinned by SHA-256 in the definition. [verify-linux-appimage.sh](../scripts/verify-linux-appimage.sh) never runs the image: it reads the squashfs at the runtime's ELF end with `unsquashfs`, checks name, version, labels and developer in the desktop entry and AppStream record, requires byte-identical payload files that pass `--selftest`, and requires the image's `AppRun cli mcp` to start its `keypaste` as the bridge, which is how a client connected from an AppImage reaches it through `~/.local/bin/keypaste`. On `osx-arm64` [build-macos-app.sh](../scripts/build-macos-app.sh) puts the same payload in an internal, unsigned and unnotarized `keypaste.app`: the payload and bridge in `Contents/MacOS`, the [Info.plist](../packaging/macos/Info.plist) with the build's numeric version prefix, since bundle versions take integers only, and the icon, licences and the [launcher](../packaging/macos/keypaste-launch.command) Terminal runs for the app's Run in `Contents/Resources`. Only its Mach-O executables and that launcher carry exec bits, which `ditto` keeps in the zip, and the script checks the bundle unzipped from that zip: the plist lints, its executable and icon exist, the launcher is executable and byte-identical to its source, the binary reports the build's version, `keypaste mcp` answers `--help`, and the app that `open` starts through LaunchServices passes `--selftest`. [build-macos-dmg.sh](../scripts/build-macos-dmg.sh) then wraps that bundle in the declared internal DMG, the one macOS package; the zip is a build intermediate that app.yml neither uploads nor attests. The selftest does not render a window, and native-file presence does not prove successful loading. Before packaging, both workflows restore the Artifact Signing dlib pinned in the definition and run [sign-windows.sh](../scripts/sign-windows.sh) over the Windows files keypaste compiles and the MSI; while `signing.policy` is `none` it signs nothing, and `authenticode` without its identity refuses before writing. A `signing_rehearsal` dispatch of `app.yml` signs with a runner-trusted certificate, checks acceptance and refusals with [verify-windows-signature.sh](../scripts/verify-windows-signature.sh), and uploads and attests nothing. Its MSI changed-byte check edits a Property value, because a byte in an unused compound-file sector lies outside the signature. Prerelease suffixes reach the binary, version check, archive name and installer. Publication requires a successful app run on the release commit; dispatch it before tagging if the push did not trigger the app workflow.

Each desktop package declares `.kdbx` without taking its default: macOS's `Info.plist` as an Alternate handler, which `build-macos-app.sh` checks in the bundle it built; Linux's `.desktop` by the MIME type `application/x-keepass2` with `Exec=keypaste-app %f`, which `verify-linux-appimage.sh` requires, and which reaches a file manager only through an AppImage integration tool; and Windows's MSI by the per-user ProgId `keypaste.Vault` and an `OpenWithProgids` value, leaving the extension's own default alone, whose rows `verify-windows-installer.sh` requires and whose removal on uninstall `exercise-desktop-upgrade.sh` requires. Whether each desktop then hands the file over is established only by installing it.

The desktop's system notifications (Q.14) are Implemented, and each platform's package has a condition no pipeline establishes. The MSI's Start menu shortcut carries the AppUserModelID `com.keypaste.app` that a request's toast posts under, which [verify-windows-installer.sh](../scripts/verify-windows-installer.sh) reads from the package; the Windows ZIP has none and posts nothing, and on Windows the locked notice is always the app's own window, because the toast has no COM activator. On macOS the notification center answers only an app bundle, and [build-macos-app.sh](../scripts/build-macos-app.sh) holds the bundle's `--selftest` to reaching it and to an add being answered. Whether an unsigned bundle can be given permission has not been tried. A request's notification on macOS is an ordinary one, which Focus can hold, since the entitlement that would let it pass does not exist ([Q.14](steps/Q.14.md)). On Linux a desktop whose notification server shows actions takes it. No platform has shown a person a notification yet, and R.1a's installed-app acts, completed before notifications existed, do not include one, so it is not established.

[verify-release-matrix.sh](../scripts/verify-release-matrix.sh) compares the definition, workflows, projects and download pages, and its fixture cases are in the script itself; R.0a introduced it. It checks the site file at the selected commit. Cloudflare deploys `site/` from pushes to `main`; [verify-site-disclosure.sh](../scripts/verify-site-disclosure.sh) checks the live page manually. Public-origin verification is covered by requirement 4 below.

[install.yml](../.github/workflows/install.yml) runs README install blocks weekly or manually on fresh runners for all four advertised targets. It verifies CLI version and MCP presence, then creates a vault and injects a value into a child. Linux ARM64 uses the definition's `install_block` substitution. Its `version` input can exercise an unadvertised candidate in `published[]`. These checks exclude later setup/use instructions and desktop installation, and are not automatically triggered by publication. [install-desktop.yml](../.github/workflows/install-desktop.yml) is dispatched with a tag and its app run: it refuses a candidate whose hash or attestation differs through [verify-desktop-candidate.sh](../scripts/verify-desktop-candidate.sh), installs the internal MSI, AppImage or DMG on a fresh runner, where Gatekeeper must first refuse the DMG's quarantined copy, and drives the installed app through [exercise-desktop-install.sh](../scripts/exercise-desktop-install.sh), where an unreachable check fails as unreached, and then performs R.1a's acts in the same installed app through [exercise-desktop-acts.sh](../scripts/exercise-desktop-acts.sh), each act's verdict in the job summary and its screenshots in the `acts-<rid>` artifact. It establishes nothing about public downloads. [upgrade-desktop.yml](../.github/workflows/upgrade-desktop.yml) is dispatched with a published CLI/MCP version: it builds three unpublished candidates at distinct numeric versions from one commit and drives [exercise-desktop-upgrade.sh](../scripts/exercise-desktop-upgrade.sh) through install, upgrade, an interrupted install, a refused downgrade and uninstall on a fresh runner, recording the user data's hashes across every transition (4.7d); on macOS the new `keypaste.app` replaces the old one through the Trash, and the link and the LaunchAgent that name its path are kept with the data (4.7e2). Either can instead be dispatched as a rehearsal before a candidate is tagged: install-desktop then installs the `-dryrun` packages of a successful app run at its own commit and upgrade-desktop makes its fixture with a CLI/MCP built from its own commit, neither verifies an attestation, and a rehearsal is never release evidence. Retain a successful run for every claimed release result.

| Upload | Bytes reach the intended destination | Fake-AWS fixtures test destination refusal; actual upload requires publication |
| Source tarball and aggregate checksum comparison | Source archive and `SHA256SUMS` agree | These checks remain inside publication |
| Desktop run resolution | The tag's `app.yml` run is found and its artifacts downloaded | [require-green-gates.sh](../scripts/require-green-gates.sh) `--run-id`, exercised by [verify-green-gates.sh](../scripts/verify-green-gates.sh) with a fake `gh` |

[verify-release-preflight.sh](../scripts/verify-release-preflight.sh) exercises changelog, version and asset checks. Its negative controls reproduce an rc heading incorrectly satisfying a release lookup and an asset count accepting a dropped target. Extract testable tag-only decisions into scripts; credential access and tag-provided inputs still require operational evidence.

## Release requirements

Completed tasks' records in [steps](steps/README.md), and Git history for tasks finished before those records existed, hold the evidence for these requirements; [STEPS](STEPS.md) holds what is still open.

1. One version and supported matrix. Recording and reconciliation through `release-targets.json` are implemented (R.0a, done). Each advertised target has a runner, CPU, package format, OS floor and evidence. Advertised binaries and `source_only` routes remain separate; `published` is append-only. Workflows and publication allowlists derive from the definition, while projects and download pages are checked against it. Preserve full prerelease versions and exact changelog-heading matches. Native installation evidence for the CLI/MCP was first recorded for 0.2.0 (R.0c, done) and is recorded per release under [Published releases](#published-releases); 4.7b and 4.7e hold it for internal desktop candidates and 4.7c2 will for public desktop downloads. Each component records whether it `publishes` archives or packages, the origin it publishes to, and the workflow whose attestation covers what it publishes; `published` is append-only and keyed on version **and** component.
2. Installable desktop packages. Provide a signed Windows installer and payload and a Linux AppImage or documented package tested on its runtime floor. The macOS desktop package is a signed and notarized DMG of the `keypaste.app` bundle (4.7a2, 3.5b). Browser downloads retain normal OS security checks. A package is published only where the definition records it signed and public under a policy that is not `none`; until then it is built, labelled internal and unsigned, and refused by the publication path.
3. Publisher verification. Check Windows signature, publisher and timestamp. Check macOS signing, notarization and Gatekeeper assessment for the desktop (3.5b); until a published release carries them, the macOS CLI stays unsigned and un-notarized as disclosed. Retain clean-machine prompts. A signature does not guarantee SmartScreen reputation, as [Microsoft documents](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation). Same-origin checksums alone cannot authenticate a publisher, so every CLI/MCP asset from `v0.3.0` onward carries a build attestation checked by the procedure in [SECURITY](../SECURITY.md#verifying-a-release); an attestation authenticates origin and is not a signature or a reproducibility claim.
4. Anonymous public installation. Download every promised asset without repository credentials, verify hashes and applicable signatures, install without an SDK, and check its version and advertised workflows. Cover injection, approval and setup where released. Desktop checks require native rendering, vault operations and CLI/app interoperability, including creating a vault in the app and opening it with the CLI. Keep the [manual desktop checklist](#manual-desktop-checklist) for behavior automation cannot observe. CLI patches do not depend on unfinished desktop features.
5. Complete publication before promotion. The completion record and public-asset verification are implemented in [release-completion.sh](../scripts/release-completion.sh) (R.0b, done, first used for 0.2.0). Verify every release before changing download pages, package-manager entries or update channels, and keep the last verified release advertised until its replacement passes. A partial upload requires a new version because published paths cannot be overwritten or reused. The recovery procedure and last-known-good promotion mechanism are deferred until after the first desktop release by founder decision 2026-10-22 ([BACKLOG](BACKLOG.md#investigation-candidates)).
6. Upgrade, uninstall and recovery. 4.7d and 4.7e2 own this evidence for the internal candidates through `upgrade-desktop.yml`; the first real-release upgrade is a dated observation at 4.7c2, against the published MSI, DMG and AppImage at the CLI's version prefix once its gates pass. Test upgrades with existing vaults, settings and client connections. Define uninstall behavior while retaining user vaults. Test interrupted upgrades and recovery, retain previous installers, record backward readability, and document backup restoration when required. Automatic updates require a verified update path.
7. Retained evidence. Record the commit, tag, hashes, URLs, signing identity, tested OS/CPU versions, installation and GUI observations, upgrade/recovery results and known limits. Keep durable links to runs or reports. Check installation after publication and periodically afterward; artifact expiry must not erase release evidence.

Advertise a target or change its public install URL only after the applicable requirements pass. Packaging and signing integration may be prepared before account enrollment, but signing claims require verified identities and delivered files.

## Installation verification

An installation is verified from the published bytes, checked against their hashes and provenance, on each claimed OS and CPU: `install.yml` does it for the CLI/MCP (see [What exists](#what-exists)), and [Published releases](#published-releases) records the results. For the desktop, `install-desktop.yml` exercises internal candidates and the list below covers what automation cannot observe.

### Manual desktop checklist

`install-desktop.yml` installs internal candidates on fresh runners and drives the installed app, and desktop tests read secret surfaces from frames Skia renders headless. Neither establishes native rendering, a browser download's SmartScreen or Gatekeeper prompt, or a person's use. Before any release that includes the app, a person runs this list on each advertised platform from the package being released, with a disposable vault holding harmless values, and records the OS name, version and build, the session type and desktop environment on Linux, the package and its hash, and each result.

**First launch and opening**

1. With no `recent.toml`, the first-launch screen says Continue agrees to the terms of use and to sending crash reports, its link opens the terms, and Continue leads to the welcome with Create a vault… and Open a vault…. With KeePassXC installed and a database open when it last closed, that database is listed first and opens.
2. Open a vault by drag and by the picker; a non-`.kdbx` file is refused before the password field. Open a `.kdbx` through the file manager's Open With, with keypaste closed and running, and KeePassXC stays the default. Drop an export, a `.env` and another file on an open vault, and drag an item onto a group.
3. Create a vault: pick a path, type the master password twice, land on an empty Items list. Cancelling the save picker writes nothing. Create over an existing vault is refused and that vault still opens with its own password.
4. A wrong password gives a calm message, stays locked and adds nothing to `recent.toml`; the right one opens the vault and records it there.
5. Do launch, unlock, the four places, a project's row, Activity and `Ctrl/Cmd+L` with the keyboard alone.

**Locking**

6. Set a one-minute timeout: the countdown appears, typing cancels it, inactivity locks, and after quit and relaunch the timeout is still one minute. Set `idle_timeout_seconds = 137` under `[[settings]]` in `app.toml`: Settings shows it, the lock comes at 137 seconds, and the file is unchanged unless the window or a list's sort changed (`[[window]]`).
7. Suspend the machine past the timeout: it wakes locked.
8. Minimize-lock, with a long idle timeout so it cannot be the cause. On: minimize (the macOS yellow button, Linux's title bar or window menu, `Cmd+M`) and restore shows the unlock screen, and a password copied before no longer pastes. Off: minimize and restore leaves it unlocked with the idle countdown on time. On again, quit and relaunch without opening Settings: minimizing locks. Switching windows, and `Cmd+H` on macOS, leave it unlocked. If a window manager reports no minimize, record that, since `MinimizeLock.IsSupported` must then omit the switch. Still unobserved on a person's macOS desktop: a minimize click and `Cmd+H`.
9. With no `app.toml` the app follows the system's light or dark setting and follows a switch while running. On a Linux desktop whose portal reports neither, choose Light, quit and relaunch: the first frame is light.

**Agents**

10. Agents › Activity lists the same records as `keypaste log` for the same `~/.keypaste/audit.jsonl`.
11. Settings › Advanced › Diagnostics names this app's process and session while unlocked. With `keypaste approve` holding the vault first, the unlock is refused and the unlock screen names it.
12. A credential request from `keypaste mcp` opens the prompt over other windows. Allow once does nothing until a second after it has focus; Enter and Escape refuse; locking takes it down. Click another window: the prompt draws inactive and its allows stay disarmed until a second after you return. Agents lists the waiting request with its seconds left; Show the prompt brings it forward with focus on Deny and disarmed for a second. After Allow once, the same request prompts again.
13. Notifications, from the installed MSI, a macOS bundle allowed to notify, or a Linux desktop whose notification server shows actions: a request made with another app in front also posts "A request is waiting for your answer" with Show the prompt, gone once answered; a second within 30 seconds posts none. Locked, an agent's first request posts "An agent asked for a locked vault" with Open keypaste on macOS and Linux; on Windows, and where notifications are unavailable, keypaste's own notice window appears. Record whether an unsigned macOS bundle can be allowed, and what a press does on Windows.
14. In Agents, Connect on an installed tool's row (such as Connect Claude Code) previews the vault, the tool's label, `--allow-run` and `--expose '**'`. Cancel leaves `claude mcp list` or `codex mcp list` unchanged; Connect adds exactly the previewed command, which from the package is the packaged `keypaste mcp`, or from the AppImage `~/.local/bin/keypaste` with `mcp`. The connection check raises the prompt, Activity then shows the release under the label, and the row says Connected. Disconnect removes keypaste from the tool.

## Delivery scope

[ROADMAP](../ROADMAP.md) owns what each release is planned to contain and [STEPS](STEPS.md) the tasks and acceptance behind it; this contract owns how any of it is published and verified. A successful CLI demo or existing installer check does not establish the desktop journey a release advertises. Package managers and agent marketplaces carry a version only after it is published and verified. Public download instructions and a route for user reports belong with the release; marketing campaigns and an announcement at every milestone are not release gates.

Every advertised behavior still requires evidence from the version that contains it. Scope changes preserve existing immutable downloads, defect disclosures and release safeguards.
