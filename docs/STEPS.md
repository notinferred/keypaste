# Build plan

This plan owns committed work, recommended order, dependencies and acceptance evidence for [PRODUCT](PRODUCT.md) v1.7 (2026-09-19, D-0243–D-0245). [FEATURES](FEATURES.md) owns the capability inventory, [RELEASE](RELEASE.md) distribution evidence, and [BACKLOG](BACKLOG.md) optional work and the [step records](steps/README.md) what each completed task did. The license remains AGPL-3.0.

This file holds open work only. Finishing a task removes it from here, adds its record and evidence row under [steps](steps/README.md), and details the next task. No row is authorized by appearing here: the founder selects what is built, and on an instruction to build the next task the first ready code row in track order is taken. No backlog item is automatically eligible.

## Current status

The public release is CLI/MCP `0.3.0`; [RELEASE](RELEASE.md) owns what can be installed and [FEATURES](FEATURES.md) owns what works in source. The desktop runs from source with internal Windows and Linux packages and no public release. The desktop, `keypaste agent` and `keypaste run` unlock separately. Since [U.1](steps/U.1.md) one vault has one owner: the app serves the vault it has unlocked to `keypaste-mcp` and a terminal approver on that vault is refused. Since [U.2](steps/U.2.md) every lock ends that session in one transition, denying what agents have waiting and zeroing their grants. Since [U.3](steps/U.3.md) the owner answers only from the vault as its file holds it: an app edit withdraws the grants for what it touched, and another program's save is refused until a person reloads. Since [4.4b](steps/4.4b.md) the app starts and ends that authority as it unlocks, locks and quits, says what agents meet as the authority reports it, names another process holding the vault, and after a crash relaunches locked and takes the endpoint over at the next unlock. The app still answers listings only, and env cards copy a command rather than launch through the app. Closing those gaps is T3 and T4; sharing, a relay and hosted services are outside the committed tracks.

## Product tracks

Track order follows the finished product: a usable password manager, a consistent lock boundary, the two integrations that depend on it, then verified distribution. Existing components are reused; completed evidence retains its original scope. Readiness can allow independent work across tracks when selected, but does not waive release checks.

## T3 — AI requests in the app

The bridge, approval gate, policy and audit writer already exist. The work is to join them to the shared session and native user interaction, with exposure and authorization still independent of unlocking.

- [ ] **4.3a — Attach MCP to the shared session.** Needs: U.1, U.2.
  **Build:** every `keypaste-mcp` request reaches the session authority U.1 establishes over its authenticated per-user endpoint, and the authority answers it through the existing approval gate. One field per release, the requested scope and TTL, the exposure rules and the protocol's size and shape limits are enforced where the vault is held, not in the bridge. A request that reaches a locked, absent or different session, or whose attachment fails, is denied and audited as a denial. The bridge never opens a vault or asks for a master password. Traces to PRODUCT §§2 and 3.2, 3.3 and 3.7.
  **Verify (V-4.3a):** a real MCP client's request through `keypaste-mcp` reaches the owning session and is answered by its gate, and the audit record names that session. An unexposed entry, a second field, a TTL over the limit and a malformed request are each refused by the authority, with the bridge unchanged. The same request with the app locked, with no owner running, against a stale session identifier and with an invalid attachment each denies and writes a denial record. A listener that only accepts a connection, or a check made only in the bridge, does not pass.
- [ ] **4.4 — Approve and deny in the desktop.** Needs: 4.3a.
  **Build:** where the app's session authority now refuses a credential request that needs a person, it asks in the app instead: the existing core `ApprovalPrompt` rendered natively with the requester, the client label, the entry and field, the requested lifetime and the agent's reason shown as untrusted text. Only an explicit Approve grants. The gate's timeout, dismissing the prompt, the bridge disconnecting and a lock each deny and withdraw it. The existing gate, grant cache, cooldown and one-prompt-at-a-time rule apply unchanged. Traces to PRODUCT §§1 and 3.2.
  **Verify (V-4.4):** a real `keypaste-mcp` request against the unlocked app raises the prompt; Approve returns the field, and the audit line records a prompted grant naming the session. Deny, the timeout, closing the prompt, the client disconnecting and a lock each return a denial with the matching method and withdraw the prompt. An agent reason written to imitate controls cannot change the prompt's layout or buttons, and the prompt's automation surface never carries a released value. A prompt driven only through its view model, or a denial observed only in the view, does not pass.
- [ ] **4.3b — Show actual requests, grants and audit outcomes.** Needs: 4.4.
  **Build:** Agent Activity shows the requests waiting at the app's session and the grants in force, with their client, entry, field and remaining lifetime, read from the session authority. It shows audit history read from the records `keypaste-mcp` wrote. A Revoke action ends one grant, or all of them, in the authority, so the next matching request is decided again. The view says when the authority or the log cannot be read instead of showing that as no activity. Traces to PRODUCT §§1 and 3.3.
  **Verify (V-4.3b):** with a real `keypaste-mcp` request waiting at the unlocked app, Agent Activity lists it. After Approve it lists the grant, and the history shows the prompted grant from the audit file. Revoke makes the same request ask again, and a lock empties both lists because the authority holds nothing. A missing or unreadable audit log is shown as unavailable. A list built from the view model's own events, or history read from anything but the log file, does not pass.
- [ ] **2.6a — Connect an MCP client from the app.** Needs: 4.4, 4.4b.
  **Build:** the app offers the clients `keypaste setup` supports (`Core/Clients/McpClientCatalog.cs`) for the vault it has unlocked, with the exposure the person selects. Before anything is written it shows the exact command it will run or the block it will print, including `--vault` and `--expose`, and it acts only on an explicit confirmation. Where a client has its own registration command, the app runs that, as `setup` does; otherwise it shows the block to paste and claims nothing. A connection check starts `keypaste-mcp` with the configured arguments and sends one `list_entry_names` and one `request_credential` through the app's session, so a real prompt, answer and audit line result. Removing the connection runs the client's own removal, so that client can no longer start the bridge for this vault. No master password, keyfile or session identifier reaches client configuration. Traces to PRODUCT §§1, 2 and 3.2.
  **Verify (V-2.6a):** from the unlocked app, connecting a client whose registration command is available registers exactly what the preview showed, and cancelling writes nothing. The check raises the app's prompt, and after Approve the audit file holds a prompted grant naming the app's session and the chosen label. After removal the client no longer lists the server, and its configuration holds no vault secret before or after. A preview composed by the view model rather than the core catalogue, or a check that only opens the pipe, does not pass.

## T4 — Project environments

An env set remains ordinary KDBX entries under `env/<project>`. Reuse the existing parser, storage and child-process injection. The app's current command-copy feature is not implementation evidence for any of the launch rows.

- [ ] **E.1a — Resolve usable project environments through the session.** Needs: U.2, U.3.
  **Build:** one core resolution reads a selected env set as the vault's owner holds it saved (`Vault.ReadSaved`, D-0317) and commits only while the requesting lifetime is live (D-0313). It checks every entry under `env/<project>` before any value leaves: a name `EnvConvention` accepts, an entry that has not expired, and one outside the recycle bin. A set with any unusable entry is refused whole, naming each key and why without its value; nothing is ever injected partially. Standalone `keypaste run` uses the same resolution and refusal with its own unlock, and its exit codes and signal behaviour stay as documented. Expiry is read through `Internal/KeePassInterop.cs`, since `VaultEntry` does not carry it yet. Traces to PRODUCT §§1.4, 2 and 3.4.
  **Verify (V-E.1a):** `keypaste run` against a vault KeePassXC made, holding an expired entry, a recycled entry and an invalid name in one set, exits non-zero naming each, starts no child and prints no value. Removing them lets the next run inject exactly the set. Through the app's session, a resolution waiting when a lock comes, and one after another program saves the file, both release nothing, and an edit made in the app is the next value resolved. A check made only in the CLI or the view, or one made after values were read into the child's environment, does not pass.
- [ ] **E.1b — Import and launch a project from the app.** Needs: E.1a, 4.4b. — Preview/import an existing `.env` through the shared parser, map a working directory and env set, and explicitly Run or Open terminal. Confirm the selected command without exposing values in arguments, logs or saved project configuration; cancellation/lock before release starts nothing. Values reach the actual child environment and no plaintext file is produced.
- [ ] **E.1c — Use the unlocked session from the CLI runner.** Needs: E.1a. — Let `keypaste run` explicitly attach to the desktop session with project authorization and no second password prompt; refusal does not silently fall back to a separately unlocked vault. Preserve documented standalone operation, exit codes and signal behavior with unambiguous mode/ownership rules.
