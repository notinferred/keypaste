# Build plan

This plan owns committed work, recommended order, dependencies and acceptance evidence for [PRODUCT](PRODUCT.md) v1.7 (2026-09-19, D-0243–D-0245). [FEATURES](FEATURES.md) owns the capability inventory, [RELEASE](RELEASE.md) distribution evidence, and [BACKLOG](BACKLOG.md) optional work and the [step records](steps/README.md) what each completed task did. The license remains AGPL-3.0.

This file holds open work only. Finishing a task removes it from here, adds its record and evidence row under [steps](steps/README.md), and details the next task. No row is authorized by appearing here: the founder selects what is built, and on an instruction to build the next task the first ready code row in track order is taken. No backlog item is automatically eligible.

## Current status

The public release is CLI/MCP `0.3.0`; [RELEASE](RELEASE.md) owns what can be installed and [FEATURES](FEATURES.md) owns what works in source. The desktop runs from source with internal Windows and Linux packages and no public release. The desktop, `keypaste agent` and `keypaste run` unlock separately. Since [U.1](steps/U.1.md) one vault has one owner: the app serves the vault it has unlocked to `keypaste-mcp` and a terminal approver on that vault is refused. Since [U.2](steps/U.2.md) every lock ends that session in one transition, denying what agents have waiting and zeroing their grants. Since [U.3](steps/U.3.md) the owner answers only from the vault as its file holds it: an app edit withdraws the grants for what it touched, and another program's save is refused until a person reloads. Since [4.4b](steps/4.4b.md) the app starts and ends that authority as it unlocks, locks and quits, says what agents meet as the authority reports it, names another process holding the vault, and after a crash relaunches locked and takes the endpoint over at the next unlock. Since [4.3a](steps/4.3a.md) the owner applies the tool's argument limits and the exposure itself, so a request that bypasses the bridge meets the same refusals, and every way of missing the session is an audited denial. Since [4.4](steps/4.4.md) the app asks about each credential request in its own prompt window and releases only on Approve, and a request whose bridge goes away is withdrawn. Since [4.3b](steps/4.3b.md) Agent Activity lists the request waiting and the grants in force, read from the session, revokes them there and shows this session's audit history. Since [2.6a](steps/2.6a.md) Agent Activity connects Claude Code or Codex to the unlocked vault after showing the exact commands, checks the connection through the registered bridge and the app's own prompt, and removes it, and the internal desktop packages carry `keypaste-mcp`. Since [E.1a](steps/E.1a.md) an env set is released whole or not at all: an expired entry or a name that cannot be exported refuses it, naming each, in `keypaste run` and through the app's session, which reads the vault as saved and releases only while the unlock that asked is live. Since [E.1b](steps/E.1b.md) Env Sets imports a `.env` and, for a project given a directory and command on this machine, opens the platform's terminal there with the set from the session after a confirmation naming the command, directory and variable names. Since [E.1c](steps/E.1c.md) `keypaste run --session` opens nothing and asks for no password: the process holding the vault asks the person about the project, its variable names, the command and the directory, and releases the whole set to the runner only on approval, while plain `keypaste run` still unlocks on its own. Sharing, a relay and hosted services are outside the committed tracks.

## Product tracks

Track order follows the finished product: a usable password manager, a consistent lock boundary, the two integrations that depend on it, then verified distribution. Existing components are reused; completed evidence retains its original scope. Readiness can allow independent work across tracks when selected, but does not waive release checks.

| T3 | AI requests in the app | A configured MCP client produces a real native request, approval/denial and a matching audit record; a locked app refuses access. | CLI setup, bridge, terminal approvals, policies and audit exist, the bridge is attached to the owning session with its limits enforced there (4.3a), the app asks and answers in its own prompt (4.4), Agent Activity shows the waiting request, the grants and this session's audit records (4.3b), and connects, checks and removes a client (2.6a); no T3 task is open. |

## T2 — One shared unlock session

These rows replaced the future terminal-owned approval architecture in D-0054, and every one is complete. ## T3 — AI requests in the app

The bridge, approval gate, policy and audit writer already exist, [4.3a](steps/4.3a.md) joined the bridge to the shared session with every request limit applied by the owner, [4.4](steps/4.4.md) put the owner's question to the person in the app's own prompt window, [4.3b](steps/4.3b.md) showed the waiting request, the grants and the session's audit records in Agent Activity, and [2.6a](steps/2.6a.md) connected a client from the app, with exposure and authorization still independent of unlocking. Every T3 task is complete.

## T4 — Project environments

An env set remains ordinary KDBX entries under `env/<project>`. Reuse the existing parser, storage and child-process injection, and resolve every set through [E.1a](steps/E.1a.md)'s `EnvResolution`, or `SessionEnvResolver` where a session holds the vault, and start every child through [E.1b](steps/E.1b.md)'s `EnvLaunch`. [E.1c](steps/E.1c.md) gave `keypaste run` the same session through the owner's endpoint. Every T4 task is complete.

## T5 — Desktop delivery

The Windows MSI and Linux AppImage are internal candidates. Existing install and upgrade observations remain useful but must be repeated for the final shared-session product. The macOS desktop, package managers and GitHub Release mirrors are optional BACKLOG items; public CLI/MCP support is retained.

- [ ] **F.20 — Diagnose the withdrawn prompt drawn on Linux.** Needs: 4.4. — app run 36040583862 at `f51fe5d`, attempt 1, `ubuntu-24.04`: `DesktopApprovalTests.A_request_withdrawn_before_its_prompt_is_drawn_never_draws_it` counted one prompt drawn where none was expected (`DesktopApprovalTests.cs:142`), its first failure in the recorded app runs. The hypothesis to test first: the test withdraws through `CancelAsync`, whose callback sets the request answered on the thread pool, and while the test awaits it the UI dispatcher may already run the show job `WindowApprovalChannel` posted, which checks `IsAnswered` only once. A branch probe repeating the case with the identical desktop test command records, in each failing iteration, whether the show job ran before the withdrawal and whether the product or only the test's arrangement lets a withdrawn prompt be drawn, per [diagnostics](diagnostics.md).
- [ ] **F.21 — End the session when the main window closes with a prompt open.** Needs: 4.4b. — Observed in [F.2b3a](steps/F.2b3a.md) on Windows 10 at `15b2c47`: with a credential request waiting in the prompt window, closing the main window with its close button left the process running with the prompt as its only window and the vault unlocked and served. The request ended `timed-out` 45 seconds later rather than `vault-locked`, and in a repeat Approve on that prompt released the value to the client (audit `granted`, `prompt`). `App.axaml.cs` ends the authority only on `ShutdownRequested`, which Avalonia's default `OnLastWindowClose` does not raise while the prompt is open.
  **Build:** closing the main window quits whatever else is open: the authority ends, a waiting request is denied as `vault-locked`, every prompt window is taken down and the process exits. A regression composes the app with a prompt waiting, closes the main window and asserts the `vault-locked` reply and that no window remains. Traces to PRODUCT §2.
  **Verify (V-F.21):** the regression fails at `15b2c47` and passes after the repair in `app.yml` on all three operating systems. Repeating the act on a real desktop is F.2b3b's.
- [ ] **F.2b3b — Observe the remaining real-desktop lock acts.** Needs: F.2b2, U.2, F.21.
  **Build:** as [F.2b3a](steps/F.2b3a.md) did on Windows, run the app from an `app.yml` artifact at a named commit, with a disposable vault and a `keypaste-mcp` configured for it, and records each act. On a real Windows 10 or 11 desktop: closing the main window through the window manager while a request waits in the prompt window, and sleeping past the idle timeout and waking. On a real Linux X11 or XWayland desktop: those two, minimizing from the title bar with minimize-lock on, with it off and after a restart ([desktop](desktop.md#observing-minimize-lock-on-macos-and-linux)), and a request arriving while another application has focus. Each result names the OS, version and build, the session type and window manager, the commit, and the audit lines the act produced. A window manager that reports no minimize is recorded, and `MinimizeLock.IsSupported` then omits the checkbox there, with a test. Traces to PRODUCT §§2 and 5.1.
  **Verify (V-F.2b3b):** the record holds every act with the source SHA. Closing the main window with a request waiting leaves `vault-locked` for it in the audit log, and waking after the timeout shows the unlock screen and refuses the next request. On Linux the prompt appears over the other window with focus on Deny.
- [ ] **R.1a — Exercise the integrated desktop candidate.** Needs: 9.4, 4.6, F.15, U.2, U.3, 4.4b, 4.3b, 2.6a, E.1b, E.1c, F.2b3a, F.2b3b.

Each act records the OS and version, the package and its hash, the commit and the audit lines it produced. Traces to PRODUCT §§1, 2 and 5.1.
