keypaste — passwords, projects and agent approvals.

A local password manager for your credentials, your projects and your AI tools. keypaste stores credentials in an ordinary KDBX file. Its CLI injects project environments and lets an agent request one credential under your approval or a rule you wrote, with a local audit record.

The planned desktop experience brings vault use, native approval prompts and project launches into one unlock session. Today the published tool is the CLI/MCP, and approvals use a separate terminal process. Local use needs no account or server.

Approve? [y/N]

The agent approval flow in one screen. An agent asked; you were shown its requester label, the requested field and its stated reason; one field goes back, with a time limit on reusing that approval. Expiry does not erase the client's copies or revoke the credential. Watch it end to end — about sixty seconds.

  • Local-first, offline Your vault is a file on your disk. Local use needs no account, service or network. Existing file-sync tools can transport the encrypted file; keypaste has no merge or managed-sync workflow.
  • Standard KDBX, not a new format CI checks KDBX read/write compatibility against real keepassxc-cli on Linux, macOS and Windows on qualifying pushes to main and every pull request. Your file remains portable; this does not claim complete KeePassXC feature coverage.
  • Open source, AGPL Auditable by anyone, forever. A tool that handles secrets shouldn't ask to be trusted on faith.

Published: CLI/MCP v0.3.0. Local vaults, environment injection and terminal approval are available on four native targets. The binaries are unsigned and there is no public desktop download. The desktop source creates and edits vaults and restores entry history, but it unlocks separately from the terminal approver. Locking the app does not stop that approver; its env screen currently copies a run command.

Install

Five lines, and the third one is the reason the other four are worth typing: it checks the archive against a hash published beside it and stops if they disagree. Each binary is a single native file, so nothing needs .NET on your machine. macOS on Apple Silicon:

curl -fLO https://dl.keypaste.com/v0.3.0/keypaste-0.3.0-osx-arm64.tar.gz
curl -fLO https://dl.keypaste.com/v0.3.0/keypaste-0.3.0-osx-arm64.tar.gz.sha256
shasum -a 256 -c keypaste-0.3.0-osx-arm64.tar.gz.sha256
tar -xzf keypaste-0.3.0-osx-arm64.tar.gz
mkdir -p ~/.local/bin && mv keypaste keypaste-mcp ~/.local/bin/

macOS 13 or later — that floor is what .NET 10 supports rather than a version this project has measured, so no run backs this floor.

Linux x64 — substitute linux-arm64 for arm64:

curl -fLO https://dl.keypaste.com/v0.3.0/keypaste-0.3.0-linux-x64.tar.gz
curl -fLO https://dl.keypaste.com/v0.3.0/keypaste-0.3.0-linux-x64.tar.gz.sha256
sha256sum -c keypaste-0.3.0-linux-x64.tar.gz.sha256
tar -xzf keypaste-0.3.0-linux-x64.tar.gz
mkdir -p ~/.local/bin && mv keypaste keypaste-mcp ~/.local/bin/

glibc 2.35 or later — Debian 12, Ubuntu 22.04 and newer. The release workflow runs the x64 binary on a clean Debian 12 and requires Alpine to refuse it; the equivalent container check is not implemented for arm64.

Windows, Intel Macs, Alpine and building from source are in the README. There is deliberately no curl | sh: it asks you to run code you have not read, from an origin that is not the repository. And the checksum proves the bytes arrived intact, not who made them — it is served from the same origin as the archive, so anyone who can replace one can replace both. The binaries are unsigned. Source-build instructions and the v0.3.0 build-attestation procedure are in the README.

Then a vault, and a project with no .env in it:

keypaste init ~/vault.kdbx
export KEYPASTE_VAULT=~/vault.kdbx

keypaste env pull dev            # imports ./.env, then offers to delete it
keypaste run dev -- npm start    # injected into the child process, nothing on disk

Running an older version?

Published versions are never rewritten here, so the old archives are still served and still broken. Replacing the binary is the fix. Full detail in the changelog.

Connecting it to Claude

The current CLI workflow uses two processes. keypaste-mcp is started by your MCP client and forwards requests without opening the vault. keypaste agent is started by you, holds the vault, and asks you the question at the top of this page.

keypaste agent --vault ~/vault.kdbx

The downloads above are v0.3.0, which includes setup: it finds installed clients and configures each through its own mcp add, and a client without one gets its block printed to paste. Only v0.1.0 lacks it — on that release use the manual client instructions instead.

keypaste setup --vault ~/vault.kdbx

Nothing keypaste writes into a client's configuration holds a master password, and nothing ever will. MCP tool calls are logged locally, granted or refused. The bridge excludes the returned field value, but request names and reasons remain and may contain sensitive text:

  time (UTC)           client       entry                decision  method
  2026-07-26 14:03:09  claude-code  -                    granted   exposure
  2026-07-26 14:03:11  claude-code  env/demo/STRIPE_KEY  granted   prompt
  2026-07-26 14:07:44  claude-code  env/demo/STRIPE_KEY  denied    out-of-scope

The planned desktop experience

The next release focuses on daily vault use and recovery, one unlock session, native MCP approvals and launching a project with its env set. Locking will stop new session-backed secret releases and launches. Values already delivered to an agent or child process remain outside that control. Sharing, hosted services, teams and complete KeePassXC parity are outside this release.
